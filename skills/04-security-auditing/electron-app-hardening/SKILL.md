# Electron App Hardening

Use when building, forking, or securing an Electron desktop app whose renderer talks to a main process. The deliverable is working code plus failing-then-passing regression tests, not a checklist-only answer.

## When to Use

- User asks to fork, rebuild, or harden an Electron application.
- A preload exposes Node modules or raw `ipcRenderer` to the renderer.
- An Electron app hosts a loopback MCP or HTTP service with file-writing tools.
- A static audit found IPC channels without sender validation.

## Procedure

1. **Scope the reusable code before copying anything.** Read the repo LICENSE and `git ls-files`; copy only files explicitly in the MIT or first-party scope. Fork with a local `git clone <source> <dest>` when the source has no remote, then remove the origin. Never carry over a proprietary main process, vendor runtime, `node_modules`, project data, or export folders. When tagging the fork, base the tag on the newest upstream tag already present in the clone, such as `<upstream-tag>-hardened`, because inventing a lower version makes the fork release look older than its ancestry.
2. **Lock the renderer boundary.** Replace any preload that exposes `fs`, `shell`, `request`, `path`, or raw `ipcRenderer` with an allowlisted bridge. Expose only `invoke` and `on`, each checking an explicit channel and event set. A sandboxed preload cannot `require()` a sibling application module, so inline the lists and add a test that parses the inline list and compares it with the shared allowlist module used by the main process.
3. **Validate IPC senders.** Route every handler through one wrapper that checks `event.senderFrame.url` against the app root or an explicit dev-origin list. Accept headless callers with no `senderFrame` so offline tests can still call handlers. Reject foreign file URLs and unlisted http origins with a plain `{ ok: false, error }` result.
4. **Harden window creation and file I/O.** Use `nodeIntegration: false`, `contextIsolation: true`, an explicit preload path, and a CSP meta tag with `script-src 'self'`. Move any inline script into an external file, because CSP will block it and a structural test should catch the regression. Let the main process own file pickers and writes through `dialog.showOpenDialog`/`showSaveDialog` instead of accepting renderer-supplied paths, because a renderer with a valid IPC channel can otherwise write anywhere the process can reach.
5. **Lock loopback services.** For any in-process HTTP or MCP endpoint: bind `127.0.0.1`, generate a token when none is configured, verify bearer tokens with `crypto.timingSafeEqual`, and reject requests whose `Host` or `Origin` is not loopback. Cap request bodies. Add tests for missing token, foreign origin, foreign host, and a valid loopback call.
6. **Write tests before each guard.** Use pure rule modules for URL and channel checks so tests exercise real code without mocking Electron. When a test must stub `electron` through `Module._load`, delete `require.cache[entryPath]` before each require that needs a different stub.
7. **Verify with a real launch.** After `npm install --ignore-scripts`, run `npm rebuild electron` to fetch the binary. Start the app under a timeout with logging enabled, emit an explicit ready log from `did-finish-load`, then inspect stderr for `CONSOLE` errors. A crash line printed at the timeout signal is not a startup failure, so rely on the ready log. For CDP browser harnesses, pin the viewport with `Emulation.setDeviceMetricsOverride` before navigation; `--window-size` sets the window, not the viewport, and headless Chrome can subtract internal chrome so media queries fire at the wrong breakpoint.
8. **Verify parity when a fork and a clean-room build both exist.** Write one canonical input to scratch, run each real pipeline through a small driver that saves artifacts in separate folders, then compare objective metrics (file count, generated tags, labels, residual directives, validation issues, bytes) plus a unified diff. A `.ks` file that still contains raw `@directives` is structurally valid but not runtime-ready, so do not call that parity. For a claim that outlives the session, commit the driver under `tests/parity/` with an env var pointing at the reference implementation instead of leaving it only in scratch. For a deterministic generator, also lock one implementation over time with a committed golden corpus and checksum manifest, regenerated by a script and verified by a single drift test. See `references/parity-comparison.md`.
9. **Package the hardened app when productizing.** Prefer the locally installed Electron dist over a downloader, flatten the app root, regenerate a minimal `package.json` with a root-relative `main`, exclude secrets and vendor code, then verify the packaged exe with a CDP smoke check. See `references/portable-packaging.md`.
10. **Report for this user in Indonesian, casual register, no em-dash.** Lead with what changed, give test counts, name any real bug found during launch, then offer three or four numbered next actions.

## Pitfalls

- Do not keep a preload that exposes whole Node modules because the app is local: any renderer script injection becomes filesystem and network access, and contextIsolation alone does not narrow an explicitly exposed module.
- When swapping a shipped host UI for a minimal shell, provide the global API the existing panels read, such as `window.getApp()` returning project name, current file, and install root; populate it from the main-process handshake or config response instead of constants, because a missing or stale shim yields empty or wrong context in the panel instead of an error.
- Do not assume a zero `electron.*` counter in a static summary means no IPC: conditional findings with an unknown loader can be absent from summary counts while still present as graph nodes, so cross-check source.
- Do not let a loopback service run with an empty token: any local process or rebinding page can call file-writing tools, so generate a token and surface it in startup output.
- Do not add framework mocks to every guard test: extract the rule into a pure module and test that module first, then add one wiring test through the real handler.
- Do not edit any proprietary editor file or bundled runtime while hardening a fork: build a new main process and load your own HTML shell instead.
- Do not call two implementations equivalent because both exit zero: compare generated artifacts from one identical input, because a minimal parser can emit `.ks` files that still contain raw directives.
- Before tagging a fork, run a fresh-checkout CI simulation that copies only git-tracked files into a temporary repo and runs the full CI there, because local node_modules, vendor files, or stale harness artifacts can make a dirty workspace pass while a clean clone fails.
