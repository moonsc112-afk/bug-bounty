# Mapping a login-time gate before the object matrix

Use this when the app presents an invite, allowlist, waitlist, or SSO restriction at sign-in. The goal is to learn which identity claim the gate reads and which credential the API actually accepts, before deciding whether an authorization matrix can even be built.

## Ordered sequence

1. **Inventory every auth route from the sign-in page itself.** Fetch `/signin` and list each form's `action` and submit buttons, then follow each start route with `curl -D -` to capture `Location`, OAuth `client_id`, `redirect_uri`, and the names of the PKCE/session cookies it sets. A route can hand off to an external IdP, while another targets a different identity backend entirely. Also check each alternate provider's own signup page for open registration: if the blocked provider is invite-gated but another provider on the same sign-in page allows self-registration, that is a separate access path worth reporting, not an exploit of the invite gate. Keep the two findings distinct.
2. **Decode the issued tokens, not the UI text.** Base64-decode the JWT payload of each access cookie and record `iss`, `sub`, `app_metadata.provider`, `email`, and `exp`. Different `iss` values across providers mean separate identity projects: a token from one provider is not portable to the other, and editing a display cookie cannot forge it.
3. **Exercise each provider with both an accepted and a rejected identity.** Record the exact error query key and message for the rejected case (for example `error=denied` versus a generic `error=failed`), and the exact wording of the denial page. The wording often names the gate's rule (staff domain or invited address).
4. **Run four separate cookie tests; do not combine them:**
   - Delete only the app session cookie, then reload. If a fresh session is minted from the remaining access/refresh pair, session creation is decoupled from the gate.
   - Set only the access JWT, with no refresh cookie. If the app clears cookies and redirects to sign-in, the pair is required.
   - Keep a valid refresh cookie and tamper with the access token. If the server silently refreshes it and stays logged in, the refresh credential is authoritative.
   - Edit non-httpOnly parent-domain cookies that mirror email or authorization. If the denial still names the signed-token email, the server validates the token, not the mirror.
5. **Check whether a failed callback leaks a usable cookie pair.** Replay the callback with a cookie jar and no redirect following, then inspect `Set-Cookie`. No access/refresh pair on the failure response means there is no cookie-race path on that route.
6. **Stop condition:** if no accepted token for an uninvited principal exists, there is no object matrix to fill. Hand the operator the precise account step needed instead of filing a login-gate finding.
7. **Label the written report by its evidence state.** Until a token from a rejected principal is replayed against the protected API and returns an authorized object, the write-up is an unconfirmed hypothesis, not a finding. Mark it as such in the document itself, list the exact replay step that would confirm or kill it, and do not submit. WHY: a chain that proves only 'the gate runs at the callback' describes architecture, and presenting it as exploitable damage gets the report rejected and burns credibility.

## CDP observation notes

- Find the browser's debugging endpoint from the listening sockets owned by the browser process and confirm it with `/json/version`. Attach to a specific page with `Target.attachToTarget` using `flatten: true`; keep the returned `sessionId` for that target's `Runtime.evaluate` and `Input.dispatchMouseEvent` calls.
- When several tabs contain the same cross-origin widget id, disambiguate frames with `Target.getTargets`: match `targetInfo.parentId` to the owning page target and match the widget id in the frame URL. Dispatching input on the wrong frame silently solves someone else's challenge.
- When a REA web observation reports `attach_limited` for network or timeline sections because another CDP client owns the target, reconstruct the redirect chain from the owning session with `Page.getNavigationHistory` rather than repeating the observation.
- A WebGL-backed canvas challenge may export as a blank data URL even while the visible tiles render. Read it from a screenshot clip instead, and record the clip origin, scale, and iframe rectangle so image coordinates can be mapped back to viewport and iframe-local coordinates.
- For virtualized combobox dropdowns (`role=combobox` custom selects), setting `scrollTop` alone does not render offscreen options. Set `scrollTop` on the actual scrollable descendant, then dispatch `new Event('scroll', {bubbles:true})` on it, then click the option. WHY: the option list is virtualized and only re-renders on a scroll event.
- To restore a saved IdP token into a CDP-controlled profile, use `DOMStorage.setDOMStorageItem` with `{securityOrigin: 'https://<idp-host>', isLocalStorage: true}`; `DOMStorage.setItem` is not a CDP method. Confirm the write with `DOMStorage.getDOMStorageItems`, then call the IdP's `/users/@me` with the token before reusing it. WHY: saved tokens expire or get invalidated by a later account switch, and a stale token sends the OAuth flow back to the login chooser.
- Name the browser surface in every handoff: a login driven through desktop GUI control lives in a different cookie jar from the CDP-managed browser used for scripted replay. Before replaying, read the account name or token in the same surface the requests will come from. WHY: a confirmed login in the other surface still yields 401 on replay, and the failure is easily mistaken for a broken matrix.
- When full-frame image analysis stalls on an anti-bot puzzle, crop to the challenge card and downscale it before re-reading, then map the returned pixel centers back through the clip origin and scale. WHY: a smaller image often completes while the full screenshot times out, and dropping the mapping makes every clicked tile land in the wrong place.

## Handing the second-account step to the operator

When the operator handles accounts personally, leave the exact login tab open and hand off rather than asking for passwords in chat. Give a short canonical URL, a clickable markdown link for the full URL, and a copyable plain-text line: long redirect URLs are unreadable when printed as a single wrapped paragraph. Ask for an explicit confirmation, then verify the account chooser or storage actually shows the new principal before running the auth flow. WHY: an account changed in the operator's normal browser is invisible to the controlled browser session, and acting on an assumption wastes the whole observation window.

If an anti-bot challenge must be delegated, leave the tab in the challenge state and state plainly that the automated attempt did not complete. Do not present a repeated, unverified solve sequence as a working method.
