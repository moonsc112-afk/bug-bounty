# ELF provenance: tying a fixture to the program it claims to be

What still works on SBPF (ELF machine 247 = v2, 263 = v1) and what to state in a report.

- **Portable static readers need no disassembly provider.** `inspect_native_exports` returns the dynamic export table; deployed programs typically export `entrypoint` and `custom_panic`, sometimes `security_txt`. `inspect_rust_binary` returns the sha256, byte size, ELF machine and an explicit "no .dep-v0" when cargo-auditable metadata was stripped (the usual case).
- **Free coherence check:** the ELF header entry address must equal the value of the `entrypoint` export. If they disagree, the file is a partial read and nothing downstream is trustworthy.
- **Identity anchor:** `grep -a -o "BEGIN SECURITY.TXT." file` pulls the program's own security.txt out of read-only data — program name, contact address, auditor list. It is a stronger identity claim than prose about which program the file came from.
- **Fixtures are the program image, not a capped dump.** A program data account is allocated at exactly 10,485,760 bytes (10 MiB) with a zero tail — that padding is the loader's, not something your fetch added. The ELF starts at offset 45 (the `ProgramData` header: 4-byte enum + 8-byte slot + 1-byte option tag + 32-byte upgrade authority), so a fixture of 10,485,715 bytes is `account_data[45:]` and is COMPLETE. Prove byte-identity before writing it in a report: hash `account_data[45:]` against the fixture (Kamino Lending `6482390f…`, Scope `0d4a3bcd…` and Whirlpool `c422b22f…` all matched their live accounts when checked this way). Only if that hash disagrees is the read partial — then say so instead of presenting the hash as the account's bytes. Two different programs reporting the same byte count is normal here and is not evidence of a cap.
- **Pre-submission drift check:** re-dump the programdata and compare against the fixture — an upgrade between PoC and submission silently invalidates the reproduction. `compare_artifacts` is the inventory-level way to check.
- **Function-level RE is off the table for SBPF**, so do not promise it: disassembly providers reject these images and stripped ones have no symtab. The behavioural PoC against the exact fetched bytes is the authoritative proof; the readers above supply the provenance around it.
