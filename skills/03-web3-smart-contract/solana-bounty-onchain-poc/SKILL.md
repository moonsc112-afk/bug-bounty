# Solana bounty: on-chain PoC against deployed bytecode

## When to Use

- A static/fuzz finding in a Solana program needs proof against the DEPLOYED mainnet bytecode (not a source recompile) before bounty submission.
- A live-config/consumer survey is needed to establish whether a proven bug has a real funds-at-risk path (severity gate).

Prove the bug in the ACTUAL deployed program. Verified with solana-program-test 2.3.x, Rust stable, WSL. Report delivery (Indonesian PDF) & submission gates (deposits, validity criteria): see evm-bounty-source-audit § Reporting & submission gates. For this operator, write findings and status replies in Indonesian without em-dash, state negative results plainly, and close with a short numbered set of next actions.

## Fetch deployed bytecode (no deps)

1. `getAccountInfo(programId, base64)` on a public RPC → 4-byte type(2) + 32-byte programdata address (base58-encode by hand if solders absent).
2. `getAccountInfo(programdataAddr)` → header 45 bytes: type(3)=4, deploy slot=8, authority option=1+32; ELF = data[45:]. Save `.so` + deploy_meta.json (slot, authority) for report provenance. Max programdata = 10MB; public RPC handles it.

## Deployed-ABI recovery and RPC simulation (no local validator)

When the program's repo is private or the SDK is stale, treat CURRENT mined transactions as the
ABI oracle, not the SDK types. Decode `getTransaction(..., encoding:"json")` instruction data from
base58 and match `sha256("global:<snake_case_name>")[:8]` against the DECODED bytes; the arg shape
falls out of the remaining byte count (a discriminator plus u32 versus plus u64). The base58 TEXT
of a longer payload does not start with the base58 of its first 8 bytes, so a string-prefix match
silently finds nothing and reads as "the instruction is never used".

For fast semantic probes, patch the arg bytes of a mined raw transaction and replay it with
`simulateTransaction(..., {sigVerify:false, replaceRecentBlockhash:true})` against live state. No
local validator, no fixtures, no compile. This is the first probe to run when only a few scalar
args are in question; graduate to ProgramTest when accounts or clock must be forged. Full recipe,
state-diff reads, versioned-transaction splicing, cap-gate denomination and the parsing traps: references/deployed-rpc-simulation.md.

A `Custom(102)` on a name the program DOES dispatch means the argument payload is stale, not that
the path is dead; rebuild the payload from a current mined tx before redesigning anything.

## Harness (solana-program-test)

- Deps: `solana-program-test = "2"`, `solana-sdk = "2"`, sha2, tokio. First build ~15-25 min (huge dep tree); CARGO_BUILD_JOBS=4 on 6GB WSL; CARGO_TARGET_DIR on native ext4 (/root/.cache), never /mnt/e.
- Loading: `ProgramTest::default()` → `pt.prefer_bpf(true)` → `pt.add_program(name, id, None)`; fixture at `tests/fixtures/{name}.so` relative to cwd. ORDER MATTERS: prefer_bpf must be set BEFORE add_program (new() registers with the flag's current value; setting it after gives "Program processor not available").
- A signer-gated replay is NOT closed just because the mainnet actor's key is unavailable. In ProgramTest substitute a generated keypair as that actor, make it the fee payer, re-derive its dependent PDAs with `Pubkey::find_program_address` (for ATAs the seeds are `[wallet, token_program, mint]` under the associated-token program id), synthesise those token accounts, and let the program's own `has_one`/signer constraints pass. Declare the substitution as an eligibility risk in the report, but never tell the operator the route is impossible before trying it.
- Every program named in a mined instruction's account list must be loaded as executable, including Token-2022 and Memo, or the handler rejects with `InvalidProgramExecutable (3009)`. Skip those pubkeys when adding fetched account fixtures, otherwise a non-executable copy overwrites the program account installed by `add_program`.
- Parse the original message header before assigning AccountMeta flags: static writable keys are indices `0..num_static_keys-num_readonly_unsigned` (signers first), followed by `meta.loadedAddresses.writable`, then everything readonly. A guessed threshold makes a treasury vault non-writable (`ConstraintMut 2000`) and reads like a deployed-build constraint; fix the flags before redesigning the account list.
- If the handler logs `WithdrawEffects { … } = Ok` (or equivalent) but the transaction ends in `UnbalancedInstruction`, fix FIXTURE LAMPORTS first: fetch each account's real `lamports` alongside its data and owner and use them verbatim; a flat `1_000_000_000` on every account makes a CPI that moves rent/lamports (observed inside a CLMM RemoveLiquidity) fail the runtime balance check even when token amounts are correct. If it still fails, calibrate the synthetic token balances from the handler's own printed `total_*_to_send_to_user` values. The tx aborts at the first failing instruction, so later instructions never appear to run; do not draw any conclusion about multi-instruction probes until the single-call control returns `Ok(())` and a before/after read of the target accumulator shows the expected delta.
- `ctx.set_account` takes `&AccountSharedData` (build `Account{..}.into()`), not `&Account`.
- Use `ctx.banks_client.process_transaction_with_metadata(tx)` — synchronous, returns result + log_messages. `send_transaction` returns before processing → immediate get_account reads STALE state (a stale read masquerades as a Clock-sysvar failure; it is a race).
- Clock control WORKS: `ctx.set_sysvar(&Clock{slot, unix_timestamp, ..})` per step; programs read the overridden values. Verify by asserting a written price's ts equals the set ts. No time-warp needed for hour/day-scale gaps. With LIVE account fixtures, derive the clock from those fixtures instead of from wall time: a clock slot below an account's stored `last_update.slot` makes elapsed-slot math underflow (KLend: `MathOverflow` in `state/last_update.rs` — `checked_sub`), while a clock far ahead trips the price-age check instead (KLend: `PriceTooOld`, max age 150 slots). Take max(stored slot across the loaded account fixtures) + 1 for the slot, and max(oracle entry timestamp) + a few seconds for `unix_timestamp`, then print both — a rejected refresh is otherwise indistinguishable from a wrong account.
- Anchor ix encoding by hand: discriminator = sha256("global:{ix_name}")[..8]; args borsh (String = u32 len + bytes; Vec = u32 len + items; fieldless enum = u8 variant index in declaration order; repr(u8) enums = u8). Create protocol accounts via the program's OWN initialize/config instructions instead of replicating zero_copy layouts — only read-side offsets need hand computation.
- Controllable price source for oracle tests: SplBalance-type entries read an SPL token account balance (value=balance, exp=mint decimals, ts/slot=Clock). Hand-craft mint(82B)/token(165B) accounts owned by Tokenkeg...; set balance per step via set_account — no token program needed. amount@64 in token account; decimals@44 in mint.
- program-test DEDUPES whole transactions: two byte-identical refresh txs in a row fail with AlreadyProcessed and silently truncate the reproducer. Prepend a UNIQUE compute-budget instruction per tx (vary the unit limit with a per-tx counter) — it also satisfies programs that require the previous ix to be compute-budget only. Any reproducer that must be re-runnable needs this; a PoC whose only evidence is a stored log from one lucky run is a cross-check failure waiting to happen. Put that instruction LAST, not first, when the transaction must satisfy a positional refresh contract — a checker that pattern-matches `Required ix <N>` by index counts instructions in order, so a prepended budget instruction shifts every position (the uniqueness that defeats dedupe does not depend on position).
- Byte-compare every fixture against its live source account before publishing (`solana program dump` / `getAccountInfo` + `cmp`/sha256) and state that byte-identity in the PoC: it is the strongest no-cheating evidence a reviewer can check in one command. Persist the live numbers a report cites (entry values, clamp equalities, pool depths, reserve fields) into a JSON artifact in the same session — numbers that live only in prose cannot be re-verified and are the first thing an independent cross-check flags.
- NEVER trust hand-computed account offsets. Scan 8-aligned 32-byte windows of a real account, batch them through getMultipleAccounts, and keep the windows that resolve to real accounts (mint 82B / token vault 165B Tokenkeg, feed 28712B owned by the oracle program, market/reserve owned by the lender): that labels the layout empirically. An off-by-8 field read yields a plausible-but-nonexistent pubkey (e.g. a market address that does not exist) and silently corrupts every downstream conclusion. A SCALAR field's offset can be calibrated the same way: search the fixture's aligned u128 slots for a value the program itself printed in its log, then read that slot before and after the transaction. Never score state corruption from a log line alone: a `SetStakeDelegated: prev:X -> new:0` line looked like erasure until a permissionless refresh with a before/after field read showed the recorded stake unchanged. Read the field, then write the claim; when a probe disproves an earlier interpretation, retract it in every draft that carried it.
- Always run a CONTROL differing only in the bug-triggering parameter (e.g. gap dt=period vs period-20s) — a flipped outcome is the strongest proof. Build the MITIGATION demo in the same harness as well: a feed of `source` + `bound` + `CappedFloored(cap == floor)` where a real swap moves the source entry while the clamped entry stays at 0,0000 % proves in one table that the protections you are NOT claiming to break do hold — evidence a reviewer would otherwise have to take on faith, and the honest counterweight to an aggressive severity claim.
- Program logs: env-gated dump of res.metadata.log_messages shows anchor msg! output (error names/numbers) — essential for diagnosing rejected refreshes.

## Live config survey (RPC, no indexer)

- Static check FIRST: grep the candidate consumer program's source for oracle/price references (e.g. `scope`, `market_price`) — zero references rules out direct consumption cheaply, before any on-chain scan. Indirect consumers (vaults pricing via lender reserve exchange rates) are already covered by the lender-reserve scan; say so explicitly instead of listing them as "unverified".
- Protocol config repos often sync mainnet JSON configs (grep commit "Sync mainnet configs"); filenames may be the OraclePrices account address, not mappings — follow the on-chain pointer fields.
- Find sibling accounts via getProgramAccounts with dataSize + memcmp filters on known pointer offsets (e.g. OracleTwaps.oracle_mappings @ offset 40). Population sweeps: prefer one memcmp GPA per (slot offset, reserve) over a single full pull, because 135k accounts x 2KB exceeds a foreground cell while 8 x N filtered calls return in seconds and each row arrives already attributed to the reserve that matched. Two silent failures to design out: memcmp `bytes` are **base58** (base64 raises `Base58DecodeError`), and under `dataSlice` the entry base is `slice_offset + 96 + i*136` in ACCOUNT coordinates — dropping the 96 still compiles, still returns rows, and shifts every key into the neighbouring entry. Chunked reads on a keyed RPC throw HTTP 429; retry 3-4 times with backoff in one shared transport helper rather than shrinking chunks.
- VERIFY A FILTER WITH A KNOWN POSITIVE BEFORE TRUSTING ITS ROWS: pick one account you already know belongs to the set (the reserve whose market you are enumerating) and assert the query returns it. A memcmp at a guessed offset does not error — it returns thousands of plausible-looking accounts that contain none of the real members, and every conclusion drawn from that row set is junk. Same for range scans: a full 8-aligned scan of a region that finds no valid program-owned pubkey is evidence about the REGION (start offset, stride, or which field leads the entry), not evidence that the accounts do not exist.
- Consumer scan: getProgramAccounts(lenderProgram, dataSize=reserveSize) then byte-search the feed pubkey anywhere in each account; read the following chain arrays. Watch INDEX COLLISIONS across feeds — verify the entry type in the SPECIFIC feed the consumer points to, live (repo config may be stale).
- Measure refresh cadence from the accumulator's last_update ts vs now: actively-keeper-refreshed sources (Δt ~1-2 min) defeat gap-based attacks in steady state; say so honestly in severity.
- Resolve consumption TRANSITIVELY, never one hop: build the entry reference graph from the synced config JSONs (twap_source / source_entry / cap_entry / floor_entry / source_entries / pyth_lazer_ema_source_entry) and BFS the closure of every consumer chain entry. A direct-source check yields false "no consumer" negatives — the manipulable primitive stays reachable through wrapper chains (MostRecentOf, MultiplicationChain, CappedFloored), so a consumer whose chain merely wraps the primitive IS a live consumer.
- Classify what each consumer actually RELIES on, not just that a reachable primitive exists: the price is the RAW price chain (multi-entry chains multiply), while the twap chain is only a tolerance guard — and that guard is VOID when (a) the twap requirement is absent (twap-divergence config = 0 → check skipped, flags set unconditionally), (b) twap chain == price chain (self-comparison), or (c) the twap is derived from the SAME manipulable source as the price — the class a tracker/stateful-logic bug defeats, because it fast-forwards the guard together with the price. Report consumers reserve-by-reserve by class.
- Re-verify every claimed consumer from LIVE accounts before any severity claim: re-parse chain arrays + consumer config scalars, record scan-vs-live drift (0 drift = saved scan faithful), and re-run the consumer scan fresh each session (a saved scan can miss reserves). Quote source-pool depth (vault balances) so impact has an economic basis.
- Per-chain account layouts, the consumer-classification table and the pool-depth recipe: references/live-consumer-survey.md — Step 4b there is the closure-walk rule that stops a `twap_chain=[]` row from being read as unprotected (a clamp inside the chain can pin the value), and the cap-only-clamp shape worth flagging as a fix requirement.

## Consumer-side (borrow) PoC — full recipe in references/

Proving that a manipulated price becomes real money needs the LENDER leg, not just the oracle leg:
deposit collateral, refresh, borrow, and a control obligation that differs ONLY in the stored price.
Verified on deployed KLend (Nov 2026): collateral USD1 0.95 @LTV 85 %, borrow 1.2 USDC accepted at
price x1.20 and rejected at the honest price with `Borrow value 1.1998 cannot exceed maximum borrow
value 1.1066` (= 0.95 x 1.3704 x 0.85, the program's own arithmetic) while >1.3 USDC stayed idle
(so the control failed on LTV, not liquidity).

Load `references/klend-scope-consumer-poc.md` for: the empirically derived Reserve/Obligation
layout table, how to derive offsets from live accounts instead of trusting a computed layout, the
market-pair selection rules (farms / deposit_limit / borrow_limit / pyth config), the exact tx
pipelines that satisfy anchor `check_refresh_ixs`, the harness pitfalls (owner == fee_payer dedupe,
signer sets), and the degenerate-CappedFloored clamp gate that decides whether a proven
manipulation is actually monetizable.

## Deployed bytecode vs public source (check before claiming any path)

A repo copy can lag or lead the deployed program. Four cheap checks, all load-bearing on a claim:

1. **Instruction inventory from the .so, cross-checked against the SDK IDL.** Extract CamelCase runs and keep the `*Instruction` names; that is the deployed dispatch set without disassembly. The `.so` stores the log literals CHUNKED (`Instruction: InitFarm` then `sForReserve` in the next run), so a plain string pass under-reports badly — diff the official SDK IDL's `instructions[]` against the repo's `pub fn` list instead: identical sets mean no hidden handler exists to audit, and a source-only name (Kamino: `execute_obligation_order` in 67 source fns vs 66 IDL entries) is the real delta. A path whose instruction is absent from the deployed set does not exist on chain, whatever the source says (Kamino KLend: `SetObligationOrder` present, `ExecuteObligationOrder` absent — and the source-side `premium/(1-delta)` monetisation died with it).
2. **Call it with the repo's discriminator.** Anchor answers `Custom(101)` (`InstructionFallbackNotFound`)
   when the discriminator matches nothing — proof by execution, not by strings.
3. **Grep the .so for a phrase a code path logs.** A distinctive `xmsg!` fragment from the source is either
   in the deployed build or not: absence means that path does not exist on chain, presence means the
   surrounding message pool is a usable specification of the deployed build's validation ORDER and its
   bounds. "Invalid <field>, must be greater than 0" with no upper clamp tells you the field accepts any
   larger value — which decides whether a live config is an operator mistake or a permitted reading.
4. **Panic-path handler inventory.** Embedded source paths (`programs/<x>/src/handlers/handler_*.rs`) list
   the handler families the deployed build carries, which settles ambiguous dispatch-name lists.
5. **Let it list its own preconditions.** A refresh-gated program answers a rejection with the exact sequence
   it demands: KLend logs `Required ix <N> <Kind>` plus the `(pubkey, index)` pairs that instruction must
   carry — in one measured case `RefreshFarmsForObligationForReserve` (naming a `reserve_farm_state` the
   public `Reserve` does not declare), then `RefreshObligation`, then `RefreshReserve`. Build the named
   sequence instead of redesigning account lists, and read the reply as a specification of which layers the
   deployed build has that the public source lacks.

Every rejection is a fact about the deployed build — the error codes form a reconnaissance loop, not noise:

| error | meaning | what to do |
|---|---|---|
| `Custom(101)` `InstructionFallbackNotFound` | discriminator matches nothing | the path is absent from the deployed dispatch |
| `Custom(102)` `InstructionDidNotDeserialize` | the NAME is dispatched, the argument payload is wrong | read the handler's `pub fn process(ctx, …)` signature and append exactly those args after the discriminator — KLend's `refresh_obligation_farms_for_reserve` takes `mode: u8` (`0` = collateral); a recognised name plus 102 is a client-side ABI gap, never a dead path |
| `Custom(6051)` `IncorrectInstructionInPosition` | the refresh-sequence contract was violated; the program reprints `Required ix <N> <Kind>` plus the `(pubkey, index)` pairs each must carry | the printed order is the REVERSE of the transaction order (the checker maps `Required[0]` to `current−1`) and any farms refresh must be appended a second time AFTER the gated instruction, since it lands in both the pre and the post contract; place the instructions that way, keep the asserted account positions, then check the GATED instruction's own variant: when a contract-conforming sequence at the demanded positions and accounts still rejects 6051, read the official SDK IDL for a `…V2` variant of that instruction and grep the ELF for its CamelCase name to confirm dispatch — KLend's redeem-withdraw V2 adds `farmsAccounts` (`[obligationFarmUserState, reserveFarmState]`, both writable) plus `farmsProgram` at the account-list tail, and taking that shape is what turned 6051 into an accepted withdrawal. A residual mismatch is a client-side ABI gap; keep reading the IDL, not the repo's handler |
| `Custom(6009)` `ReserveStale` | `refresh_obligation` wants a reserve whose `last_update.slot` equals the CURRENT slot, while the required order puts `RefreshReserve` after it | the program-test bank clock is fixed, so refresh the reserve in a transaction of its own first; the freshness carries into the main transaction |
| `"Padding fields must be zeroed"` | argument layout drift | rebuild the args from the official SDK's IDL, not the repo's struct |

Chain build and run so a failed compile CANNOT fall through to the previous binary: `cargo build … | grep -E 'error|Finished' && ./bin` exits with grep's status and silently reruns yesterday's artifact, whose output then reads like a fresh result of the new code. Use `cargo build --bin X || exit 1` (or assert on a line only the new build prints), and when a run contradicts the patch you just applied, suspect the stale binary before suspecting the program.

Measure the state gates too: read the flag bytes the handler checks (e.g. Kamino's
`obligation_order_creation_enabled` at `repr(C)` offset 3306 of the market account — 0 in all 52 markets)
and confirm the offset by letting the deployed program enforce it: patch the fork byte and watch the
`OrderCreationDisabled` gate open. Map the whole flag block from the SDK IDL's ACCOUNT layout rather than the
source's declaration order — the IDL lists fields in deployed order, so anchoring one verified flag offset on
its sequence reads the neighbours (with `obligationOrderCreationEnabled` pinned at 3306, the two live bytes at
3310/3311 resolve to `borrowOrderCreationEnabled`/`borrowOrderExecutionEnabled`, i.e. the reachable live
surface is the borrow-order book, while obligation-order creation stays 0 in every market).

### Kamino order args (deployed layout, differs from master)

`set_obligation_order(index u8, order)`, order = 128 B: `condition_threshold_sf u128`,
`opportunity_parameter_sf u128`, `min_execution_bonus_bps u16`, `max_execution_bonus_bps u16`,
`condition_type u8`, `opportunity_type u8`, `padding1 [u8;10]`, `padding2 [u128;5]` — both paddings zeroed,
no trailing `min_expected` argument. Master declares named mint fields plus that trailing argument; sending
that shape is rejected with "Padding fields must be zeroed". Re-derive such layouts from the official SDK
tarball's IDL (`npm pack @kamino-finance/klend-sdk`, then `src/idl/*.json`) instead of guessing.

### Remaining-accounts counts are per-call, not static

`refresh_obligation` wants exactly `deposit_count + borrow_count` **at that moment** (`utils/accounts.rs`
parse). One reserve works before a borrow and fails after it with `Custom(6006)` plus an explicit
`expected_remaining_accounts=…, actual_remaining_accounts=…` xmsg — read that xmsg from the logs before
redesigning account layouts.

When 6006 instead names a specific collateral index whose stored slot is zeroed/default, feed EVERY slot
from zero through the highest populated one with its literal stored pubkey before redesigning anything. If
that faithful per-slot list still rejects, the mismatch is the deployed build's own view of the obligation,
not the client ABI: classify the candidate as blocked-by-deployed-view and stop tuning account order.

When a successful withdrawal's account list OMITS the debt reserve because the build counted no borrow, the
stranded liability is proven structurally: a transfer that never receives an account cannot decrement its
borrow aggregate, and if the program closes the obligation in the same transaction the debtor identity is
gone too. Prefer that argument over hunting for the aggregate's byte offset, and quote the dollar figure as
"recorded on the obligation", not "read from the reserve". A panic log's `file:line` also belongs to the
DEPLOYED revision, so reading that line in the repo copy can name an unrelated function; verify the framing
bytecode first rather than treating the printed line number as a source pointer.

### Obligation borrow entries (deployed KLend)

Borrow slots start at **1208** with stride **200** (the u64 at 1184 is `lowestReserveDepositLiquidationLtv`, not a slot), and the borrowing reserve pubkey sits at **entry+24** — not at
the entry's head, where the bytes are rate/amount data that decodes into plausible-but-nonexistent
pubkeys. Next to the deposits (96, stride 136) and the SF totals at 2208/2224/2240/2256
(deposited/borrowed/allowed/unhealthy); the deployed build's own active-borrow flag `hasDebt` is at **2287** and a 0 there means no liquidation can be built on the account however large its stored debt fields are. Derive all of it from the SDK IDL's `types.Obligation.fields` — IDL order IS deployed order, whereas a source struct walk drifts. Scan the whole account for
program-owned pubkeys to settle such an offset instead of probing candidate field positions: on a $48M
obligation that scan named the market, both deposit reserves and the debt reserve in one pass, while four
hand-guessed offsets had found nothing.

### Borrow-order book (the live order surface): guarded — do not re-audit

`borrowOrderCreationEnabled`/`borrowOrderExecutionEnabled` are the flag bytes that are ON in live markets
(see the flag-block rule above), so the reachable order surface is the borrow-order book, not obligation
orders. The fill path (`handler_fill_borrow_order.rs` v2 + `state/borrow_order_operations.rs`) was audited
(Nov 2026) and holds: destination bound to the order's stored `debt_liquidity_mint`/
`filled_debt_destination` (`check_accounts_match_order`), expiry (`BorrowOrderFillTimeLimitExceeded`),
amount caps (`BorrowSize::AtMost` + `min_borrow_order_fill_value` + `check_order_remaining_debt_value`),
rate ceiling (`reserve_config.max_borrow_rate_bps() > order.max_borrow_rate_bps` → reject; a config max,
so conservative in the right direction), term + maturity (`is_term_satisfied` against the configured term
and against `seconds_until_maturity`), and the exec-enabled gate. The filler drives the borrow as
`owner = payer` — by design for a standing order, and the guards above are what make it safe. Still unread:
the rollover-execution body and the state of the two rollover/migration flags (their bytes sit outside the
market's mapped flag block).

### Market-wide autodeleverage: no floor, no rate cap — measure debtors first

The deployed build lowers the LTV at which *anyone* may deleverage a reserve's positions once that
reserve's deposit or borrow limit is crossed: `eligible = 1 - bps_per_day/10_000 * days`, from 100 % down,
saturating at zero (no floor), and the only deployed bound on the rate is "greater than 0" — live values
reach 7200 and 48000 bps/day. This is a config-class lever, not a proven loss: of 1400 obligations touching
the seven reserves with enabled clocks and 0 % thresholds, **zero** carried a borrow the deployed build
recognises, and a liquidation must repay debt. Establish the debtor population (the deployed build's own
`borrow_count`, see above) before attaching any severity to an autodeleverage finding. Then test the two sets
for DISJOINTNESS instead of scanning one side: match every obligation's borrow entries (stride 128, reserve at
entry+24) against the clock-running reserves, and read each matched reserve's `autodeleverage_enabled` — a
borrower population sitting on feature-off reserves, plus enabled reserves with no borrowers, means the branch
has no reachable victim whatever the clocks say (measured: 148 reserves with running clocks, a healthy
$5.3 M borrower among 40 on them, and `enabled=0` on every reserve those borrowers touched). One-sided matching is the classic error: the branch fires on EITHER a crossed deposit limit on the obligation's collateral reserve OR a crossed borrow limit on its debt reserve, so also collect the obligations that DEPOSIT each clock-running reserve and screen those through the deployed build's own `hasDebt`/`borrow_count` before claiming a victim — on this population the deposit side surfaced 1,157 obligations and every one was a debtless ghost, which makes the branch inert for the opposite reason and is itself the finding (references/liquidation-refresh-contract.md). Two doors in this family are closed by ABI evidence, not prose: the SDK IDL gives `markObligationForDeleveraging` a `lendingMarketOwner` signer, so permissionless marking is not the route in; and the withdraw-ticket *progress callback* IS in the SDK IDL, but on the instruction named `enqueueToWithdraw` (accounts `progressCallbackCustomAccount0/1`, arg `progressCallbackType`), not on an instruction whose name contains `ticket` or `callback`. Search an IDL by instruction SEMANTICS and by account/arg names, never by a user-facing concept word: a name-only grep reports a false 'not in the IDL' and sends you to a needless ELF hunt. The deployed ELF independently carries `WithdrawTicketProgressCallbackAccountsMissing` / `InvalidWithdrawTicketProgressCallbackConfig`. A hand-built probe with two dummy custom accounts established the enum: `progressCallbackType` 0 and 1 deserialise and then hit `Custom(3012)`, 2 and 3 return `Custom(102)` (`InstructionDidNotDeserialize`). Proving arbitrary CPI still requires satisfying the 3012 gate, so park it with that named condition rather than claiming a clean surface.

Read the clocks
at their validated offsets, not guessed ones (`DEP_TS=280`, `BOR_TS=288`, feature flag at config base
`4856+94` on an 8624-byte reserve) — a self-calibrated sweep over hand-picked byte ranges returns a silent
zero that reads as "no affected reserves".

### Reading live scalars without an IDL

Walk the repo's structs for RELATIVE offsets only, then calibrate the absolute base on live data: find a
field whose value pair is unique and self-describing (a reserve's `(loan_to_value_pct, liquidation_threshold_pct)`
pair pinned the config base in one scan), take `base = anchor_offset − relative_offset`, and confirm with two
independent witnesses — values the deployed program itself enforced (vault accounts its own constraints
accepted, an available-liquidity number that produced an insufficient-liquidity error) and the plausibility of
the whole population's values for the neighbouring fields. A text walk mis-sizes nested structs and drifts
silently (`LastUpdate` read as 8 B instead of 16 shifted every later field by 8), and a struct-size assert
against the live account size catches only whole-struct errors, not shifted fields. A conservation-identity search (`mint_supply ≈ available + borrowed`) is only as good as its inputs: a collateral-mint offset learned on ONE reserve is not universal, and `mint_supply < available` on another reserve proves that input is wrong, not that the reserve is broken. Reject a winning hypothesis whose decoded value is 0 on every reserve: that is a padding field, not an aggregate. A search that passes those checks still counts only as a verified negative on the method, not as evidence that reserve accounting is sound.

Before joining a saved sweep JSON to fresh RPC reads, decode one sample row end to end: print the keys the
row actually carries (not the ones you remember writing) and read one known field from one account.
A stale key name or a `dataSlice` shorter than the field yields zeros, and zeros read as "no positions" — the shape of a silently empty result. When changing what a tuple holds, change its serializer in the SAME edit: an `enabled` byte replaced by a day count but still saved under the old keys silently becomes `None` at join time. For autodiscovered address sets, print the snapshot's first few hundred bytes and assert the collected values' owner/size profile against one known member before trusting any zero: a recursive collector takes the FIRST string-valued key it finds, so a snapshot whose reserve field is `pk` yields a set of `mint` addresses instead, and successive scans then "discover" zero hits for entirely different reasons. An **empty per-entry array** in a saved scan is the same trap one level deeper: a row whose `borrows` list is empty while the obligation's own account plainly carries debt means the entry parse failed, so take health from the obligation's aggregate totals (they were cross-checked row by row) and never quote per-entry breakdowns from a source you have not validated on one known-positive row.

**Resolve an account set from the instruction that already touched it.** When a byte-level read cannot pin an address, stop reading hex and read the chain instead: `getSignaturesForAddress(<the account you care about>)` → `getTransaction` (decode per the traps above) → the matched instruction's account list is ground truth exactly as the deployed program used it. An obligation's own `refresh_obligation` transaction lists its deposit reserves then its borrow reserves in the deployed build's own counting order — that resolved a debt reserve after two blind offset attempts failed — and the same list is evidence of how the deployed build COUNTS that account's state.

**Find a PDA by asking the chain, not by hand-rolling curve math.** Accounts that no imported helper can derive (a farm user state, a per-owner metadata account) fall out of a 256-way bump sweep: build every candidate as `sha256(seeds ‖ bump ‖ program_id ‖ "ProgramDerivedAddress")` and send them in ONE `getMultipleAccounts` — the address that resolves to a real account owned by the expected program is the PDA, and the sweep doubles as proof that the account exists (a 920-byte farms user state turned up at bump 255 this way). Take the seed recipe from the repo's own helper rather than the docs (`utils/seeds.rs`: KLend's obligation farm user state is `[b"user", farm_state, obligation]` under the farms program id), and when the source's `farm_collateral`/`farm_debt` offsets read as non-existent addresses on the live reserve, treat the farm state the deployed build names in its required-ix log as the real one — the deployed layout has moved those fields. With no farm named, resolve the pointer by scanning the reserve's 32-byte windows for an account owned by the farms program (validate the scan on a reserve whose farm state is known first), and expect a FARMLESS reserve to need no farms step at all: the deployed build answers `NoFarmForReserve` (6050) and the gate moves to the plain V1 path, so classify candidates by whether the deposit reserve has a farm before assembling the transaction.

**A stored aggregate is not the deployed build's view, and the common benign cause is a completed repay.** Before calling a non-zero stored debt field a defect, byte-verify three things on every victim: the active-debt flag (`hasDebt`), the occupancy of the borrow slot array (count of non-zero bytes across the full region), and the stale flag. A cleared flag, an empty slot region, and `stale=1` together describe the intended post-repay state. In that state a refresh recomputing zero borrows, a full collateral withdrawal, and `ObligationBorrowsZero (6023)` on liquidation are all expected behaviour, not a freeze or an extraction. Derive the borrow-region base and stride from the SDK IDL's account `types` order, not from a source struct walk or a `0xff` marker: an off-by-24 read lands in padding and manufactures a fake "borrow region" full of sentinel bytes. A control with `hasDebt=1` and populated slots is mandatory, but reaching liquidation math on the control proves only that the wiring works, it does not convert the repaid victims into findings. When a byte-level check disproves a class, retract it in the same pass across the finding file, coverage ledger, draft, addendum, send guide, and checksum manifest, then re-verify with `sha256sum -c`; a stale claim left in any active artifact is what gets submitted. Consequence for the lending money paths: references/lending-money-paths.md.

### Token-2022 mints and optional account slots (fixtures)

When a fixture mint is Token-2022, the harness needs that program loaded, and `add_program` only accepts names it recognises from the fixtures directory: dump the on-chain Token-2022 programdata ELF to `tests/fixtures/tokenzq.so` (the name is recognisable, "token2022" is not) and register it as `tokenzq`. Then match the token program slot to the SIDE whose mint is T22 — the repay/liquidity mint's program guards the repay accounts, the collateral mint's program guards the withdraw accounts — because swapping them surfaces as `ConstraintMintTokenProgram` (2022) or `InvalidProgramId` (3008) on the account that pairs with the wrong one. A pool whose collateral is T22 and whose debt is plain SPL therefore needs T22 only on the withdraw side. For optional accounts that are absent, an empty slot is not accepted: `Option<AccountLoader<…>>` still demands an account owned by the expected program (`AccountOwnedByWrongProgram` 3007 on the system program), while a `Program`/address-constrained slot rejects anything but its exact key — so pass a real, correctly-owned account (a sibling farm account works) rather than a placeholder.

A deposit instruction's destination collateral is the RESERVE's cToken supply vault (`#[account(address = reserve.load()?.collateral.supply_vault)]`), never the depositor's ATA — passing a derived ATA fails with `ConstraintAddress` (2012).

Before authoring a PoC, list `src/bin/` for an older `*poc*` binary aimed at the same instruction: an unwritten-but-unrun PoC from an earlier pass is free reconnaissance — building it costs a compile, and its first failures (an account-count rejection, a missing farm ix) are the deployed build teaching you the contract. Port its constants into a new bin rather than starting from a blank harness, and keep the fixture prefix per target (`ldN_*`) so two victims can coexist without clobbering each other's files.

## Honesty rule

Logic bug proven on deployed bytecode + conditional economic impact = reportable High with explicit preconditions; do not claim Critical without a live consumed path that ALSO passes the monetization gate — the consumer must be Active with LTV > 0 (a structurally reachable but Hidden/Obsolete or LTV=0 consumer cannot be exploited through collateral; read its live ReserveConfig before ranking escalation targets, and rank by Active + LTV, not by structural match alone). State what was NOT verified (other consumers, verifiable-build match). Quantify the exposure before fixing the rating: sweep the lender's positions, compute the price drop each deposit would need to exhaust its headroom, aggregate the debt that becomes liquidatable at each drop threshold, and join every reserve with the protection that actually holds its price. Then compare the cost of producing that drop (pool depth) against the payoff (liquidator bonus, or the extra borrowing capacity an inflated price unlocks): a real mechanism that is unreachable at a profit is High, and the quantified boundary plus its error bar belongs in the appendix — pushing the rating up without those numbers, or leaving the boundary unstated, is what a reviewer tests first. Recipe and reference numbers: references/klend-live-layout.md.

Before concluding that a live-data source is blocked, spend one call on the cheapest falsification: fetch a known account of the program and compare its `owner` field, character by character, with the program id your query used. An empty `getProgramAccounts` on EVERY endpoint is more often a one-character id typo than a provider policy, and that mistake hardens into a wrong "the provider refuses this program" note that costs weeks.

## Binary-level RE limits (verified Nov 2026)

Deployed Solana program ELFs are eBPF (ELF machine 247) and STRIPPED (.text + .shstrtab only, no symtab/debug, no .dep-v0 cargo-auditable section). rea-agents' Ghidra provider rejects eBPF ("unsupported ELF architecture"); GNU objdump/readelf show zero symbols. Do NOT promise function-level binary confirmation of a Solana bug — the behavioral program-test PoC against the exact fetched bytes (+ sha256 provenance via rea inspect_rust_binary, which works on eBPF for hash/format evidence) is the authoritative proof. MCP stdio servers configured but not loaded in-session can be driven directly: spawn `node <server>.mjs mcp` with the config's env, speak JSON-RPC (initialize → notifications/initialized → tools/call), checkpoint responses to disk; each spawn is a fresh session (Evidence does not persist across spawns — export the bundle in the SAME process that produced the records).

Provenance that DOES work on SBPF — the portable static readers, `security_txt` extraction, the entry-address coherence check and the padded-dump tell — is in references/elf-provenance.md. Two rules stay live regardless: quote a hash only as a fixture hash unless byte-identity with the account was proven, and re-dump the programdata before submitting, because an upgrade between PoC and submission silently invalidates the reproduction.

## Program rules decide the payout, not the prose (checked on Kamino #433, Nov 2026)

Read the program page before writing a submission. On a live Sherlock bug bounty the report's writing style is never mentioned; the rules specify evidence instead: a working reproducible PoC on a local validator or LiteSVM with signature verification and runtime checks enabled, starting accounts faithful to mainnet (balances, owners, authorities, config), and an attack realistically executable in funding, permissions and ordering.

The clause that kills harness shortcuts, quoted: "Directly editing accounts, inventing balances or authorities, bypassing checks or assuming excluded privileged actions does not establish eligibility." A PoC that writes the manipulated oracle value into an account, or seeds a position account directly, lands at most in the discretionary bucket (Kamino pays up to $2,000 for "artificial-state reports") even when the underlying bug is real and proven. Drive the vulnerable state through real programs and instructions instead: clone the AMM and execute an actual swap so the oracle prices it, and build positions with the programs' own init instructions. Where a shortcut is unavoidable, disclose it in the report and keep the money claim on the reproducible part.

Owner-signed instructions need the owner's key, which the mainnet owner's key is not (and should not be): repoint the account's `owner` field at a funded test key and DECLARE the substitution. The instruction's own `has_one = owner` constraint still has to pass and the actor stays the natural one (here, the borrower withdrawing their own collateral), but treat the substitution as an ELIGIBILITY RISK, not a settled rebuttal: the program rule says directly editing accounts or inventing authorities does not establish eligibility, and eligibility is judged before severity. Quote that clause verbatim in the report, state which part of the proof is visible in program logs before any signature matters, and which step needs the substituted key. Keep the defect evidence independent of the substitution: the deployed build's own log must state the defect (its refresh recognising a deposit and no borrow) before any signature is in play.

Two more clauses decide borderline reports. "An attacker-reachable vulnerable state need not have occurred previously on mainnet. Reproduce the transactions leading to it." answers the objection that a needed keeper gap or lull was never observed live: drive the deployed bytecode into that state under a controlled clock and say openly that the natural precondition was not seen. "Route available under the production conditions at submission", together with the warning against "merely arranging transactions in the desired order in a local test", means the exploit's actual route must be an instruction any eligible actor can call on a listed instance; name that route explicitly rather than letting the harness arrangement stand in for it.

Second rule with teeth: covered production instances are only markets/vaults officially listed in the protocol's normal UI workflow. An instance reachable only by pasting a public key or URL parameter is out of scope, so verify the market is UI-listed before building an impact story on it. Also check the public audit repository for the same prior finding (a confidential known-issues list may still exist). Oracle-handling bugs are explicitly assessable, including bypassing configured freshness checks.

Ship the enumeration with the report: an appendix tabulating every candidate (market, listing status, LTV, tolerance, the protection that actually holds it), a rule-by-rule table quoting the program page clause next to your position on it, and an explicit "what we do not claim" list (no assumed steady-state exploit, no funds-at-risk claim in a non-covered instance, funding models named as such). Reviewers test exactly those three things, and a report that states the bounds against it first cannot be answered with "the other markets must be protected" or "you overclaimed".

## Kamino/Scope + Orca practical traps (verified Nov 2026)

Check listing before building any impact story. `GET https://api.kamino.finance/v2/kamino-market` returns the market config the app is built from (with `isVisibleInUi` per market), and `GET /v2/kamino-market/<addr>` returns `{"error":"Market <addr> not found in config"}` for anything unlisted. A market can be live on mainnet, own real reserves, and still be absent from that list; on Kamino #433 such a finding is not a covered production instance, so its funds-at-risk claim is unpayable however clean the PoC is. Reserve to market mapping: bytes 32..64 of the Reserve account; market owner at bytes 24..56 of the LendingMarket (version u64 @8, bump u64 @16).

Do not dismiss a `CappedFloored` clamp as useless before decoding its bound entry. Decode OracleMappings from the chain: with 512 entries the bases are price_types 16392, tolerance 16904, twap mask 17928, ref price 18440, 20-byte generic 19464 (58 bytes per entry, 8-byte discriminator first). When a wrapper entry's decoded source list comes back all zeros or `u16::MAX` for every entry you touch, treat it as a misaligned `generic` base, not proof that the wrapper has no sources: recompute the base from the account length (`8 + 512*32 + 512 + 1024 + 512 + 1024 = 19464` for 512 entries) and re-read one known-positive entry before claiming no transitive path. Why: a 512-byte drift lands in the ref-price array, whose `0x0000`/`0xFFFF` values decode as empty source lists and manufacture a false "no consumer" result. A bound of oracle type 27 (`DiscountToMaturity`) is computed from discount parameters and the maturity date, so swaps cannot move it and the clamp is a genuine mitigation. Types worth knowing: 12 ScopeTwap1h, 13/14 OrcaWhirlpoolAtoB/BtoA, 23 FixedPrice, 27 DiscountToMaturity, 28 MostRecentOf, 33 CappedFloored, 43 MultiplicationChain, 52 ExponentTranching.

Decode every bound a candidate sits behind, then enumerate — never generalize from the one reserve you happened to test. Two numbers decide manipulability besides the clamp: a `MostRecentOf` (type 28) rejects its whole entry when the smallest and largest source differ by more than its own `max_divergence_bps`, and rejects sources older than `sources_max_age_s` — that divergence, not the lending-side tolerance, is usually the binding cap (observed live: 30-1200 bps); and a `CappedFloored` with `cap_entry == floor_entry` serves the bound, so the price is pinned exactly when that bound is not market-derived. Run the cross-check as a table over all spot/LP-reachable reserves: reserve | market (Reserve @32..64) | listing status from the protocol's own config API | LTV | lending tolerance | price path | what actually protects it. If the heavy `getProgramAccounts` enumeration is throttled or empty, the same classification still works from a candidate set via `getMultipleAccounts` on keys already collected plus the config API for market metadata — heavy full scans belong on a cloud box or a keyed RPC. Run multi-minute sweeps as a tracked background job (`terminal(background=true)`) and consume its completion notification — shell `nohup`/`disown`/`setsid` wrappers are refused because the platform tracks the process itself — and have a sweep that depends on a fresh edit assert the edited line is present in the file before it starts, or a lost edit resurfaces as a crash that reads like a new finding. For a keyed endpoint, the cheapest route verified (Nov 2026): a free Helius key from dashboard.helius.dev — $0, no card, 1M credits/month, `getProgramAccounts` at 5 req/s costing 10 credits per call — or QuickNode's free plan; the key lives in the endpoint URL (`https://mainnet.helius-rpc.com/?api-key=...`), so have the operator write that one line into `rpc_url.txt` beside the sweep script instead of pasting it into chat, and keep it out of the report. When that endpoint is later refused, probe before re-planning: `getBlockHeight` first (a standard call) and only then the heavy method — a bare `Unauthorized` HTTP 401 on BOTH probes means the key itself is not recognised, however perfect its shape (a syntactically valid UUID still 401s), while a failure confined to `getProgramAccounts` is a plan or method restriction. The mix-up to check first on Helius: the dashboard's Project ID is a UUID too, so a copied project id authenticates nothing — re-copy from the API Keys row with its own copy button, not by selecting the text. Validate cheaply with `scripts/check_rpc_endpoint.py` before spending a sweep on a bad endpoint; it accepts either a full URL or a bare key in `rpc_url.txt` and never prints the key. Two parsing traps worth designing out: the placeholder in the example line must be ignored (a `xxxx`/PASTE URL otherwise gets tried as a real key), and a URL that sits on a commented-out line should still count, because an operator who edits the example in place leaves the `#` in front of it. Create that placeholder file yourself before asking — an operator told to fill in a file nobody created burns a round trip, and "I cannot find rpc_url.txt" is what that instruction sounds like on the other side. Offer a one-liner that writes the secret straight to disk without it crossing the chat: `read -rp "paste RPC URL: " U && printf '%s\n' "$U" > rpc_url.txt`. Make the reader tolerant of a half-filled file — skip `#` comment lines, strip a UTF-8 BOM, still honour `SOLANA_RPC`, and print a loud warning when the run is on a keyless public endpoint, because there `getProgramAccounts` returns an empty array that reads as "no positions" rather than "blocked". Keep such scripts dual-host: derive output paths from `__file__` with an env override and be sitting on an env RPC, since a path hardcoded for the cloud box fails on Windows and silently costs a rerun. Before reporting a blocked data source, spend two calls on the tool surface itself: check whether a provider account is already connected, and search the environment's skill/plugin catalog for a domain tool (a scanner skill or an RPC-provider skill changes the plan) — both are cheaper than a week of hand-rolled substitutes. And when the operator asks whether the whole toolset was actually used, answer with a used-versus-unused inventory (tool → what it would add here → verdict) and then DO the highest-value unused thing in the same turn: the portable static readers that still work on SBPF ELFs, a catalog skill that scans the same sources with different eyes, or a watchdog that replaces a fragile background process are all one call away, and an inventory without the action that follows it is the failure mode.

KLend position setup without seeding accounts: `init_user_metadata` takes owner, fee_payer, the `[b"user_meta", owner]` PDA, the optional `referrer_user_metadata` passed as the program id when None, rent, system, with arg `user_lookup_table: Pubkey` (`Pubkey::default()` is fine). `init_obligation` takes obligation_owner, fee_payer, the obligation PDA, lending_market, seed1_account, seed2_account, owner_user_metadata, rent, system, with args `tag: u8, id: u8`; for tag 0 both seed accounts must be `Pubkey::default()` (the system program id) because that value is part of the PDA seeds. Twenty lines removes the "accounts were seeded" objection.

Reconnaissance before writing the swap: read a real transaction. `getSignaturesForAddress` on the pool → `getTransaction` (jsonParsed) → `meta.innerInstructions` shows the account order the caller used, and the instruction data decodes to `u64 amount, u64 other_amount_threshold, u128 sqrt_price_limit, u8 is_amount_in, u8 a_to_b`. Treat that ordering as the CALLER's shape, not the program's struct: extra accounts (a second token program, the memo program, both mints, router PDAs) belong to a router's CPI layer. When a struct field fails its check the error names the field — `AccountNotSigner 3010` on `token_authority` pins that field's POSITION; do not infer the interface from a router's account list. Expect a Scope-sourced pool's recent transactions to be mostly `RefreshPriceList`, not trades. Four encoding traps when mining that history: `getTransaction` with `encoding: "json"` returns instruction `data` as **base58** — compare it against sha256 discriminator bytes after a bs58 decode, never against the hex digest, or the match can never fire and you will conclude the instruction was never used; instructions in that encoding carry `programIdIndex`, not `programId`, so resolve the program through `accountKeys[index]` or a `programId == …` filter silently matches nothing; versioned transactions keep address-lookup keys in `meta.loadedAddresses` (writable then readonly) appended after the static `accountKeys`, so index into the concatenation; and `getBlockTime` can be unavailable for the current slot (`Block not available for slot …`), so read `slot − 64` or fall back to local time when the math is day-scale.

Executing a real Orca swap locally, verified end to end (Nov 2026): load the deployed Whirlpool ELF plus the pool, mints, vaults, tick arrays and oracle accounts as fixtures; the `token_authority` slot only has to be *a signer* (the mainnet routers pass a plain system-owned wallet, not a whitelisted PDA), so your own funded keypair works and no router program is needed. Account order that the deployed program accepts: token_program, token_authority(signer), whirlpool, owner_a, vault_a, owner_b, vault_b, tick_array_0, tick_array_1, tick_array_2, oracle; args are `u64 amount, u64 other_amount_threshold, u128 sqrt_price_limit (MIN for a_to_b, MAX for b_to_a), u8 amount_is_input, u8 a_to_b`. Three traps: (1) set the bank clock *after* the pool's stored `reward_last_updated_timestamp` or the swap dies with `InvalidTimestamp 6022`; (2) the tick-array slots must follow the swap direction (a_to_b walks down: 0 then -1408; b_to_a walks up: 0 then +1408) and deeper arrays may be uninitialised, which surfaces as `TickArraySequenceInvalidIndex 6038` and is the real ceiling on how far a single manipulation can push the price; (3) the same run can drive the deployed Scope program's `refresh_price_list` against the pool afterwards, which proves the price the protocol serves moved without any oracle account being written by hand.
