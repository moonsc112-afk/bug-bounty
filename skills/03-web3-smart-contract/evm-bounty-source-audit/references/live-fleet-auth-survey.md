# Live-fleet config survey for Auth/authority protocols (BoringVault-style)

When the program scope is a FLEET of deployed contracts and root cause may be "deployed configuration", survey the live authorities instead of only reading code:

- Sherlock bug-bounty pages: Details tab carries rewards/known-issues/rules; the contract list lives at `?tab=scope` (query param, not a text tab). Parse the scope innerText as address/label pairs (filter blank lines first — navigating raw innerText without stripping empties silently yields empty labels and zero coverage).
- Authority model (solmate `Auth` + `RolesAuthority`): every sensitive fn is `requiresAuth`, so the audit question is "what is public?". For each in-scope contract read `authority()` live, then `isCapabilityPublic(authority, target, selector)` — **eth_call must be sent TO the authority address** with (target, selector) as args; sending it to the target returns revert=false-negative for the entire fleet. Validate with a positive control (`canCall(randomAddr, target, sel)` true for a selector the config file marks public, false for a role-only one) before trusting a clean sweep.
- Re-run the capability survey when a later-acquired source bundle adds selectors. A fixed signature table from an earlier pass cannot cover functions that did not exist when it was built: derive every signature from the newest verified ABI (`cast sig` on exact signatures), read the target's `authority()` live, and sweep all selectors again. When a role holder is a contract rather than a Safe, fetch its verified source and check `requiresAuth` on its entrypoints before calling it a permissionless path. Why: a new teller generation can expose a trusted capability while an older all-false sweep still looks clean.
- Classify cluster members by NAME PATTERN from repo deployment records (`Teller*`, `Queue*`, `*Solver*`, `Manager*`, `Accountant*`, `Pauser*`) — keyed lookups miss variants (TellerWithLayerZeroRateLimiting, ChainlinkCCIPTeller) and understate coverage.
- **Verify live cluster coherence before any deeper claim.** For each in-scope vault, read every member's pointer back to the vault (`manager.vault()`, `teller.vault()`, `queue.boringVault()`, `accountant.vault()`) and compare against the in-scope vault address: a member pointing at a DIFFERENT vault is a real configuration-bug class (funds routed to the wrong book) and costs one batched sweep per chain. Veda: 189 pointers / 48 clusters / 0 mismatch. Take the teller from `vault.hook()` read on chain — deployment records go stale (record teller vs live hook can differ in address AND params).
- Veda-style repos record `contractMetadata.auditGap` per deployed contract (= what the audit did not cover). Treat it as a lead index, not fact: diff the DEPLOYED source (Blockscout v2 `api/v2/smart-contracts/{addr}`) against the repo — observed gaps were metadata artefacts (queue byte-identical, solver/teller simply older versions).
- Public `bulkWithdraw` (and any teller path that skips `beforeTransfer`) bypasses share-lock/deny-list/permissionedTransfers; whether it pays depends on LIVE `shareLockPeriod()`, `permissionedTransfers()`, deny-list usage — read those before framing impact, and expect partner-vault configs to be deliberate (present on freshly deployed vaults).
- `canCall(user, target, sel)` / `isCapabilityPublic` must be called ON THE TARGET CONTRACT'S OWN AUTHORITY, never another contract's (asking a manager's authority about vault calls returns false for everything — a silent full-fleet false-negative). Sanity-check any all-false sweep with a positive control (a selector the deployment config marks public must come back true).
- Mapping the LIVE merkle permission set: Veda-style repos ship `leafs/**/*.json` (per-vault metadata with ManagerAddress + ManageRoot + every leaf's TargetAddress/selector/AddressArguments/LeafDigest + the full MerkleTree; solmate MerkleProofLib = sorted-pair keccak). Find the live strategists by scanning `ManageRootUpdated(address,bytes32,bytes32)` logs (Blockscout `/api/v2/addresses/{a}/logs`, paginated) and then read `manageRoot(strategist)` live — the JSON root matches the live root only for vaults whose file is current; the rest rotate roots and their live leaves are opaque. Audit the matched sets for leaves whose AddressArguments bind fewer addresses than the signature's address params; router leaves (`1inch/Odos swap(...,(struct),bytes)`) and order-mint leaves (Ethena `mint((order),...)`) legitimately leave the beneficiary/executor slot unbound — strategist-controlled by design, out of scope unless a permissionless execution path exists.
- Invariant-fuzz harness for a copied queue/accountant: an `assert*` placed inside a `try { externalCall() { assert... } }` SUCCESS body aborts the entire handler call and is NOT caught by that try's catch — the branch silently stops executing and the suite passes vacuously. Always add a hand-built sanity test proving each handler action really executes (and its payout math), and remember the queue's `safeTransferFrom` needs a user approval in setup.
- RPC quirks: `rpc.monad.xyz`, `rpc.gobob.xyz`, `rpc.tempo.xyz` 403 without a browser User-Agent; WSL `git clone` into `/mnt/e/...` can die on `shallow.lock` — clone with native Windows git into `E:/` instead. Probe the provider's `eth_getLogs` window cap before declaring an event scan impossible: on Monad 1000/10000/50k-block windows error but 100-block windows succeed, so scan narrow windows around a known deploy/config block, or read mapping/state directly. Derive log topics with `cast sig-event` from the DEPLOYED ABI, not memory (Solmate `RolesAuthority` emits `UserRoleUpdated(address,uint8,bool)`; a guessed `uint8,uint8` topic silently returns zero logs). Historical `eth_getCode` worked there, so binary-search the first block with code to find the deploy, then scan around it. A full-history scan under a 100-block cap is a bounded negative: name the unblock (indexed logs or an Etherscan V2 key) instead of claiming exhaustive coverage. When computing selectors from source signatures for a bytecode diff, canonicalize contract types (`ERC20`/`IBufferHelper` → `address`) or every comparison against live bytecode manufactures false 'unknown selector' entries.
- **Deployed teller VARIANTS must be selector-scanned before trusting any "variant not deployed" claim** — earlier passes (yours or a parallel session) that probed a config getter with the WRONG ARITY (e.g. `currentBufferHelpers()` with no argument) get a revert and record a false negative. Scan each in-scope teller's bytecode for variant selectors (`setDepositBufferHelper` 0xb4bf379c, `setWithdrawBufferHelper` 0x9428fcd4, `allowBufferHelper` 0x0d1598dd, `disallowBufferHelper` 0xb032299c, `cancelRemediationAndUnlockShares` 0xf15ad97a, `vestingState` 0x32a633c0, `depositCap` 0xdbd5edc7, `version` 0x54fd4d50) and read `version()` strings — they compose ("Yield Streaming V0.1, Buffer V0.1, Base V0.2", "Base V0.3" = NOT in repo). Veda case: 14 live Buffer/YS tellers (~$140M TVL) were missed by two independent passes that had concluded the variants were not deployed.
- **Buffer-helper wiring is per-(teller, asset) and gets toggled**: enumerate via the teller's `DepositBufferHelperSet`/`WithdrawBufferHelperSet` events (Blockscout v1 `?module=logs&action=getLogs&topic0=` works on eth.blockscout.com; Ink = explorer.inkonchain.com same shape; Monad/Tempo/Plasma RPCs cap getLogs ranges hard — read `currentBufferHelpers(asset)` directly instead) or read the struct live. `getDepositManageCall` output is executed by `vault.manage` WITHOUT merkle verification; inputs = (deposit asset, amount) with amount user-set — the admin-set helper delegate is a total vault-control surface. Audit the helper AND the destination's live availability: a 4626 whose deposits are closed (`maxDeposit`=0, custom error on `deposit`) bricks every deposit atomically because `_afterDeposit` runs unconditionally inside `_erc20Deposit` (Veda mUSD case: $63M vault deposits live-reverting). `ERC4626BufferHelper`/`MorphoMarketBufferHelper` carry no audit marker; `AaveV3BufferHelper`/`HastraPrimeBufferHelper` do. Pre-simulate the helper's exact manage target call with `from = the vault` to prove/falsify the live path.
- **Legacy/archived sibling contracts stay live and in-use** — repo `src/archive/**` code (Veda case: AtomicQueue `0xD45884B5...`) can still be the contract users approve TODAY. Fetch the DEPLOYED revision (Blockscout `additional_sources`, repo history at the deployment commit): the current source may gate a function (`solve` gained `requiresAuth`) while the deployed revision is permissionless. Measure live usage from event logs (block ranges of `AtomicRequestUpdated`/the site's event) and per-request solvability with `viewSolveMetaData(offer, want, users[])` (flags: 0 = solvable; otherwise one bit = zero-amount/deadline/balance/approval). A fill pays the user their RECORDED price, so fresh requests ≈ market = not theft; stale-price or never-expiring (`deadline = uint64.max`) requests are the harm case. Veda case: the remediation hook (freeze when a live approval to the blocked spender exists) already makes the class known for triage; a residual on other series = direct-disclosure note, not a submission.
- **Deployed parents can lag HEAD — grep the parent, not just the child.** A verified child source is often thin (e.g. LayerZeroTeller ~11 KB); the parent (`TellerWithMultiAssetSupport`) sits in the SAME Blockscout response's `additional_sources` (search all entries for the function you're auditing). Deployed parents are older vintages than repo HEAD — confirm live semantics (e.g. `vault.exit(..., msg.sender, shareAmount)` = the caller burns their OWN shares → a public `bulkWithdraw` is benign) before framing an access-control observation as a finding.
- **Check the owner Safe's transaction queue before claiming a privileged change is impossible.** Query `https://api.safe.global/tx-service/<chainShort>/api/v1/safes/<EIP55-address>/multisig-transactions/?limit=100` (for Arbitrum `chainShort=arb1`). `/transactions/` is a 404, and lowercase addresses are rejected: checksum them first. Read `isExecuted` for pending items and decode `dataDecoded.parameters` to recover `diamondCut` `_init` and `_calldata`, then compare `_calldata`'s 4-byte selector to known initializer signatures. WHY: source search sees deployed code but cannot see a queued upgrade or role change that is already signed.
