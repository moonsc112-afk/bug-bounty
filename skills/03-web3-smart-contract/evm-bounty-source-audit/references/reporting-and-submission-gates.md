# Reporting and submission gates

Moved out of SKILL.md (size). Load this when a finding survives validation.

- Before submitting, open the program's submission flow and validity-criteria docs. Severity options determine deposit requirements (Sherlock bug bounties: Critical/High require a USDC deposit — $250 at last check — refunded if the report is valid, forfeited if invalid). Submission login is email verification / wallet on the OPERATOR's account: never commit funds or credentials autonomously; present the deposit + severity trade-off and let the operator decide.
- Before quoting a 'profit is capped by X' bound, run a short parameter fuzz that tries to EXCEED it and trace the exact expression the cap feeds; a draft capped at 100 DOLA was falsified by a fuzzer observing 541 DOLA because the cap bounded the subtracted term, not the result.
- Program criteria often require High/Critical to DEMONSTRATE funds at risk from realistic production states. A proven logic bug with only conditional impact may not meet that bar — survey live consumption first (which downstream programs actually read the affected entry, and how often it updates) and frame severity honestly instead of overclaiming to justify the deposit.
- Survey technique + PoC recipe: solana-bounty-onchain-poc skill (live config survey, consumer scan, MAIN-vs-CONTROL proof).
- Write ONE draft per distinct ROOT CAUSE, not per observed symptom: fold the impact proof (e.g. the lender-side borrow against a manipulated price) into the parent finding's PoC section — a second submission whose root cause is the first one's consequence gets closed as a duplicate. Tell the operator which drafts to file, in what order. When the program pays $0 for Medium/Low, do not open standalone tickets for impact-limited root causes: carry them as 2–3-line informational notes at the end of the paying submission (and never attach the other draft), so the work is visible without adding zero-value submissions that pollute triage.
- Drafts must be paste-ready against the platform's form fields: Title / Severity / Vulnerability detail (code refs as file:line) / Impact / PoC (verbatim commands + the observed program log lines) / Recommendation / Honest bounds / Evidence. Ship a short guide mapping each heading to a form field, list what to attach, and note the deposit/validity criteria without deciding them for the operator.
- The final deliverable is a BUNDLE directory: one paste file per distinct root cause (the finding alone, whole, as the paste unit), a judge-facing appendix, an operator-language README that is the only file with instructions in it, and a `MANIFEST.sha256`. Build it by COPYING the delivered drafts and patching only what the newest evidence changes — never re-type a draft into a bundle, and treat assembly as the last verification pass: re-check each factual claim against the artifacts as they stand (rewrite the SENTENCE, not the hash, when the wording is the imprecise part — an identity claim must name the byte range that makes it true), add evidence that arrived after the draft, and re-hash fixtures against the live source because an upgrade between PoC and submission silently invalidates a reproduction. Generate the manifest by script and verify it in the same call (`sha256sum -c` → report the OK count and zero FAILED) before handing it over: a manifest never recomputed is the cheapest thing for a reviewer to falsify. Judge-facing files carry facts about the target, never narrative about the agent's own process — internal corrections, retracted claims and tooling mishaps stay in `findings/`, while the honest-bounds sections stay in the paste text because they are what make the severity rating credible. Prepare the FAQ the operator will face at triage, phrased exactly as the report states it (why this severity and not higher; what is synthetic in the PoC and what is real; whether funds moved; whether the mechanism is instance-specific or a class), so nobody improvises a stronger claim than the evidence. Recipe and the bundle's file-by-file rules: references/submission-bundle.md; start the operator README from templates/operator-submit-readme.md.
- Every number in a draft must be extractable from an artifact you can point to (a log line, a JSON read-back) — quote logs VERBATIM rather than paraphrasing. **Aggregate figures you summed by hand across several runs** (total calls, total withdrawal attempts, totals across campaigns) are the highest-risk numbers in a deliverable: recompute them with a script from the per-run values and grep EVERY artifact for the stale variant before shipping — a hand-sum drift sits far from the sentence a reader checks and only surfaces when a reviewer adds the parts up themselves.
- Every quoted project rule/policy must be locatable in the repo (README/docs/config). If grep does not find it, drop the quote and restate the point from your own verified survey — an unsourced "the project's own rule says X" is the fastest way to lose credibility on an otherwise real finding.
- State the live BOUNDS inside the draft (which comparable targets are protected by a clamp/guard, how much liquidity the demo actually had), and never claim funds were moved unless they were. Bounds stated up front read as rigor; the same bounds discovered later by the reviewer read as overclaiming.
- Unverified-but-in-scope contracts (no source, and bytecode no decompiler handles — EraVM/ZK-Stack): the productive pair is (a) a paste-ready verification request naming the exact implementation addresses, why each matters (name the verified contract that wires it in, e.g. the price feed behind the vault), an offer to re-check once published, and ONE concrete function-level check the source would unblock — the exact residual question plus file:line refs for the half of the logic that IS readable plus an explicit 'we are not claiming this is the case'. A generic 'please verify' reads as nagging; a specific low-cost question shows the work, gives the team a reason to answer, and its answer may itself be a fund-loss lead (Fulcrom case: does the unverified OrderBook transfer each order's collateral to the Vault in the same frame as the vault call, as the verified router path does? If not, that is cross-user collateral mis-attribution). Then send it on the team's own channels (their docs page's socials section lists Discord/Telegram/X) and state plainly that you cannot post from their account, offering the local-browser route as the alternative. Validate the route before proposing it: the Discord invite API (`GET discord.com/api/v10/invites/<code>?with_counts=true`) returns the guild name, member count and expiry, so an invite is confirmed live and correctly attributed rather than assumed; and the protocol's own FAQ usually states which channel owns which class of issue (protocol mechanics → their Discord, funds/UI weirdness → the venue the user traded on) — read it (GitBook serves a `.md` variant with the FAQ answers expanded, but fetch it in a real browser: a plain HTTP client can return an empty 200 for the same URL). You cannot enumerate a server's channels from outside (`guilds/<id>/preview` needs auth, the widget endpoint is usually disabled), so hand over the post-join steps instead (join → pass the verify gate → post in the support channel) and warn that community managers never DM first, so a DM claiming to be admin is a red flag. Never hand the operator an unvalidated link: give its provenance (which official page it came from) and its live status; plus (b) a change-detector so publication is caught without the operator remembering: a Hermes cron job whose `monitor` is a deterministic script (the path must be a bare filename under `~/AppData/Local/hermes/scripts/`; identical stdout suppresses the agent run, changed stdout wakes it with a diff) checking `s3FileKeys` presence, Sourcify status and the proxy's impl slot — never put a timestamp in its output or every tick looks changed. Start from this skill's `scripts/explorer_verification_probe.py`.
- **The PoC attachment (platforms with "PoC Required"): build it from a FRESH run, never from stored logs.** A stored log re-presents an earlier failing/older run as current evidence — a `deficit.log` left over from before a geometry fix printed `4 passed; 1 failed` inside an otherwise green appendix. Re-run every suite and every live-read immediately before generating, then gate the built artifact: grep it for `[FAIL]`, `[stderr]`, `Error:`, `command not found` and fix the generator before sending. Recipe and section list: references/submission-poc-appendix.md.
- **Delivery kits ship as TWO files: an operator-language kit and a 100%-target-language payload.** The kit (channel table, send steps, short + long variants) stays in the operator's language; the payload file is the message ALONE, no scaffolding, because that is what gets pasted or attached and a reviewer must never see send-instructions. Machine-check the split before handing it over: every non-empty payload line must appear verbatim in the kit (`[l for l in payload.splitlines() if l.strip() and l not in kit] == []`) plus a scan for operator-language words — a rewrite that silently drops a paragraph is invisible otherwise. When asked to translate a section, first check what is ALREADY in the target language and say so: translating an already-English payload means removing the scaffolding, not rewriting the message.
- Submission skeleton to copy: `templates/sherlock-submission.md`.
- Encrypted submission for programs that accept an age-encrypted `report.age` instead of body text (Merkl-style): fetch the program key (`curl -sL https://github.com/<handle>.keys -o merkl.keys`), encrypt `age -R merkl.keys -o report.age report.txt`, then verify the recipient before sending — output starts `age-encryption.org/v1` and its `-> ssh-ed25519 <b64>` stanza prefix must match the key's fingerprint prefix from `ssh-keygen -l -f merkl.keys`. Only the recipient can decrypt, so the header+fingerprint check IS the validation (a wrong-recipient ciphertext looks fine otherwise); validate the toolchain itself first with a throwaway `age-keygen` round-trip. Run these via WSL (on this host: `apt-get install -y age`) and never put `$()`/backticks inside the `wsl.exe bash -lc '...'` string — see references/local-arsenal.md.
- Getting the mail out (email-based programs): default to handing the operator a copy-paste kit — exact Subject line, plain-text body (title-level summary of each finding + payout address), and `report.age` copied to the Desktop for the attach picker (sha256-verify it through the new path; warn that Windows hides `.txt` so the folder shows "report" next to "report.age" — attach ONLY the `.age`). Let the operator send from their own client. Ship the kit as files (subject, body, steps in the operator's language) AND as a copyable chat block; merge several disclosure-class items into ONE email with numbered sections. If they ask the agent to send instead: `scripts/send_report_email.py` + a locally-filled app-password ini (never accept a password in chat; never echo it), SMTP pre-flight + dry-run first, then IMAP Sent-folder verification. Recipe: references/email-program-submission.md. Follow-ups/addenda: body-only (no attachment), sent from the SAME address, subject referencing the original submission; keep code findings separate from ops notes so triage can close the notes without a ticket; and re-verify every subagent-claimed mechanism with a local test before writing it down — a claimed "silent burn" (toggleAllowance(distributor)) turned out to be a hard revert in the actual run.
- **Validate the disclosure CHANNEL BEFORE promising delivery.** Inventory the real options in one pass: (a) the project's X account — a profile-level "Message" button can still land on "has a closed inbox" (X blocks non-follower DMs); open the compose pane and read its text before writing anything; (b) published security address — grep docs site, SECURITY.md, footer; if none exists do NOT invent security@, use the developer addresses from the repo's own `git log --format='%ae'` ranked by commit count (Veda: alberto@veda.tech 170, ryan@ 118, benjamin@ 37); (c) pages the project itself links can be STALE — Veda's footer Immunefi link 404s; load them instead of trusting them; (d) whether the operator's machine has a usable session for the planned channel — check login-cookie NAMES (never values) in the browser profile DBs to pick the right profile, and note that a Hermes connector listed with connected=false cannot send (no mail CLI/connector = the operator sends from their own client).
- **Driving the operator's real browser (computer_use) to send as them: clicks are reliable, typing is not.** Clicks dispatch per-element events to the captured element, but Chrome refuses background TYPE/KEY ('background_unavailable') and foreground delivery is global SendInput to the ACTIVATED window — it can land in a DIFFERENT Chrome window than the one captured (observed: an unrelated window navigated mid-task). Minimize free typing: prefer one short navigation plus clipboard paste (`cat file | clip`, then foreground ctrl+v). Verify the paste in a fresh capture BEFORE pressing Enter, re-capture after every foreground action, and open a dedicated new window for the whole flow instead of reusing one the operator is actively using. X DM compose deep links: x.com/i/chat -> New message -> type the handle -> pick the suggestion (verify the handle — lookalikes abound).
- Assemble the aggregate `report.txt` with a builder script, never by hand: split each draft on its `---` separators, assert every expected marker survives (copy-paste notes replaced by appendix pointers; per-report payout blocks stripped so exactly ONE placeholder remains), then append the full PoC sources verbatim from disk. Ship operator-supplied values (payout address) as a marked placeholder plus a one-line re-encrypt command so finalizing is one edit + one command, not a rebuild. When finalizing: edit the plaintext FIRST, then `rm -f report.age` before re-encrypting (age/age-keygen refuse to overwrite an existing output), and record the on-disk sha256 of BOTH artifacts — hash the file as written, not the builder's in-memory string (Windows text-mode writes convert LF→CRLF, so those two hashes differ).
- PDF delivery: first try the documents env — `export PY="$(hermes pm environment documents --extra documents --extra documents-pdf)"` (persisted venv with reportlab/pypdf/pdfplumber on this host, verified); build from a JSON spec via the pdf skill's `scripts/pdf_create.py` (elements: heading/paragraph/table/pagebreak; keep table cells <60 chars), then `pdf_page_image.py` + vision-check the table pages for clipping. If that env is absent: write the report as HTML with print CSS (@page A4) and render via Playwright — launch with the explicit executable `E:/tools/playwright-browsers/chromium-1255/chrome-win64/chrome.exe` (machine-wide PLAYWRIGHT_BROWSERS_PATH; plain `pw.chromium.launch()` may not find it), `page.pdf(format='A4', print_background=True)`. Screenshot a page and vision-check before sending: literal `&lt;code&gt;`-style artefacts and unbalanced emphasis are the usual defects.
- Pre-empt `already identified in a prior audit` rejections for partner/extension contracts: pull the prior audit's in-scope FILE table (competition READMEs carry in-scope/out-of-scope file lists; check the AI-auditor disclosure doc for mentions too) and confirm your contracts were NOT in scope — partner/token-wrapper dirs are commonly listed explicitly out of scope (Merkl's 2025-11 audit: in-scope = `DistributionCreator` + `Distributor` only; `contracts/partners/tokenWrappers/**` out). State that fact in the submission so triage cannot wave the finding off on that clause. Also read the FULL published findings list of that prior audit, not just the scope table: the C4 report page is a JS app (web_extract/curl return only the shell — render it with a browser and save `document.body.innerText`), then grep it for your subsystem's keywords. Merkl case: 4 Medium + 5 Low published, zero "wrapper" mentions → no overlap; and the two candidates deliberately left unreported (onClaim callback error handling, stale merkle root during disputes) turned out to BE published findings — the full read is what validates which near-misses were already known.
- Reward-expectation questions: anchor only on published data. A program that publishes no per-severity amounts (Merkl does not) still has a severity-definition table — grade expectations per finding against it honestly (strongest candidate vs acknowledgment-only), calibrate ballpark only from the same org's other programs (Angle's older Immunefi/Hats program: Medium $2,500, High $20k), and never invent numbers; name the first-reporter rule as the reason to submit immediately. Grade each candidate against the award-table ROW before proposing to file (hardening rows are credit-only even with a PoC; own-funds-only findings stay hardening).
