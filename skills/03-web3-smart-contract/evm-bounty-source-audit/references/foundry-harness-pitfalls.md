# Foundry harness pitfalls when extending an existing test suite

Use these rules when writing a local `.t.sol` harness that inherits an audit target's existing tests.

- Redeclare file-level constants you use from the parent test file, or import them explicitly. Solidity imports are not transitive for file-scope symbols, so a derived contract sees the parent contract but not its file constants. Why: compile fails with `Undeclared identifier` after a wasted edit cycle.
- Match the harness contract by name and grep the log for your own `testFuzz_` case. A derived contract inherits every parent test, so suite totals can look healthy while your new fuzz case never ran. Why: `forge test --match-contract X` reports inherited tests as part of X.
- Prefer `vm.expectRevert(...)` over `fail()` inside a `try` block for expected failures. `fail()` reverts, and the surrounding `catch` swallows that revert, so a negative test passes even when the call unexpectedly succeeds. Why: the assertion never escapes the catch.
- Keep Solidity import paths case-sensitive on Linux. `contracts/Libraries/` fails when the file lives in `contracts/libraries/`, and `forge test --match-contract` still compiles every test file, so one stale import in an unrelated test blocks the focused suite. Why: the compiler sees the whole test tree before filtering by contract.
- Expect double-wrapped revert data when a call goes through a diamond `diamondCut` initializer. Inspect the raw revert bytes first; when an `Error(string)` is nested inside another `Error(string)`, match it with `abi.encodeWithSignature("Error(string)", abi.encodeWithSignature("Error(string)", "msg"))` instead of the bare string. Why: the init call bubbles the inner revert as the outer string payload.
- If you need a post-call assertion, set a boolean flag inside `try` and assert it only after the `catch` block closes. Any assertion placed inside `try` is caught and discarded on failure.
- Drop `view` from a test that calls `vm.expectRevert`. Cheatcodes are stateful, so the compiler rejects a `view` function that uses them.
- Cast fuzzed `uint8` values to `bytes1` when assigning into a `bytes` buffer, and watch for `uint8`-to-`bytes1` implicit-conversion compile errors.
- Add `using Lib for Type;` inside the derived contract even when the parent file already declared it. `using` directives are not inherited.
- Import struct types you return from harness calls by their qualified name when they come from another file; symbols imported by the parent file are not re-exported.
- Grep the test tree for helper and mock names before reusing them. Hand-rolled helpers often reimplement an older signature and compile only on the shard you did not run.
- Verify remappings with `forge remappings` instead of assuming a `src/` prefix is ignored: a `src/=src/` remapping resolved `src/interfaces/IBufferHelper.sol` correctly in a project whose `foundry.toml` also set `src = "src"`. If imports instead resolve to `src/src/...`, use a neutral key such as `@proj/` and rewrite the target tree's imports before building. Why: guessing the remap shape turns a configuration detail into a false harness failure.
- When a verified source closure lacks third-party dependency files, copy the closure to scratch and add the smallest stubs that match the imported signatures exactly, including indirect base constructor arguments. Why: swapping in a different library version changes selectors and compiler errors, which invalidates the bytecode-match evidence you are trying to preserve.
- When a fuzz case calls a vendored helper that reads ERC20 state through an address parameter, bind that parameter to a deployed mock contract rather than an arbitrary fuzz address. Why: `allowance()` on a non-contract reverts with `call to non-contract address`, which reads as a protocol bug but is an unseeded fixture.
- Before asserting a calldata shape for vendored code, read the function body and assert the exact target and index order. A buffer helper can send two `approve` calls to the asset and only the third call to the ERC4626, so `target[1]` is the asset, not the vault. Why: a plausible-looking expectation produces failures that look like helper bugs and costs a debug cycle.
- Establish one green happy-path test before trusting any negative or fuzz harness. Run the valid call first and assert its state change, then add malformed-input cases. Why: a broken setup makes every reverting input look safe, and a `try/catch` campaign reports PASS while the code path was never entered.
- If the project's own Hardhat suite already carries the valid setup (recapitalization, reserve ratios, season state) and the Foundry mock cannot reproduce it, copy that suite and add the hypothesis there instead of patching the mock. Why: a hand-built deposit mock can enter a different revert path, producing green negative tests that never reach the code under test.
- When a Foundry project's `package.json` uses an unsupported npm protocol such as `workspace:*`, install only the Solidity-imported packages into a scratch npm project and copy `node_modules` into the target. Why: Foundry compiles Solidity sources and does not need the monorepo JS toolchain; a full install fails on the workspace protocol before any contract builds.
- When a fuzz case reverts on a cap, allowance, or balance precondition, inspect `setUp` and seed helpers before widening the assertion. A seed that already fills the deposit cap makes every later deposit revert with the cap error; shrink the seed instead of treating the revert as protocol behaviour. Why: the failure is in the harness budget, not in the code under test.
- Before buying a deep invariant campaign, probe the parameter extremes the shipped harness bounds away (time warp, rate, caps) with a cheap deterministic loop: `vm.snapshot()`, warp by each step, wrap the call in `try/catch`, then `vm.revertTo()`. Classify reverts that require a privileged role or a far-future timestamp as non-payable. Why: a default 10-day, moderate-rate fuzzer cannot falsify an overflow boundary, and a multi-hour campaign is the wrong first instrument.
- Assert the check site, not a stronger invariant than the code promises. A deposit cap enforced inside `_mint` against `totalAssets()` at call time is not an invariant that `totalAssets()` stays under the cap after later yield accrual. Why: the stronger assertion produces a failing test that reads like a bug and burns a lead.
- An upgradeable whose constructor calls `_disableInitializers()` will revert `Initializable: contract is already initialized` when a fresh local deployment calls `initialize()`. Set the owner directly with `vm.store(address(c), bytes32(0), bytes32(uint256(uint160(owner))))` after reading the real slot from `forge inspect <Contract> storage --json` (do not assume slot 0 for every inheritance layout). Why: a proxy-free test still needs an owner for `onlyOwner` setup, and calling the initializer is a dead end by design.
- Casting an `address` literal to a contract type fails when that contract has a payable fallback/receive (`Explicit type conversion not allowed from non-payable "address"`). Use `MyContract(payable(addr))` in the test. Why: the compiler rejects the cast before any test runs, so a wiring assertion looks like a build failure.
- Solidity address literals require EIP-55 checksums even when they came from an API in lowercase. Batch-convert with `cast --to-checksum-address <addr>` (or `cast --to-checksum-address` per line) before compiling; compiler error 9429 prints the corrected form anyway.
- Pass the custom error's exact arguments to `vm.expectRevert(abi.encodeWithSelector(Err.selector, ...))`. Encoding only the selector fails with `Error != expected error` when the error carries payload, which looks like the wrong revert but is a matcher bug. Read the actual values from the failure line and encode them.
- When a target resolves a requested amount against the position's real balance (an entitlement or repay router that caps requests at the debt actually owed), seed the fixture with AT LEAST the amount under test. Otherwise the boundary test silently exercises the capped amount and the expected value is off by a whole order of magnitude.
- Oracle valuations are `amount * price / 10**assetDecimals`, with `price` quoted per whole unit at 18dp. A 1-wei price on an 18-decimal asset values a 1-wei position as ZERO, not 2. Pick price and amount together so the intended rounding boundary is actually reached, and compute the expected value independently before writing the assertion.
- Compute boundary constants in a separate interpreter, hard-code them in the test, and add an assertion that the neighbouring amount falls on the other side of the boundary. WHY: a test that only checks the accept case passes even when the rounding direction is wrong.
- In Morpho Blue `liquidate` harnesses, `seizedAssets` and `repaidShares` must have exactly one zero (`UtilsLib.exactlyOneZero`); passing both, or both as `type(uint256).max`, reverts `inconsistent input`. Seed a real borrow first, then pass `seizedAssets > 0` with `repaidShares = 0` and let Morpho derive the repayment. Why: a two-sided input fails before the callback and reads like a health or access-control failure, wasting a debug cycle.
- When a collateral wrapper's `depositAssets`/`depositShares` supplies straight into the lending market, assert the lending position's collateral, not the user's wrapper ERC20 balance. Why: the wrapper mints to itself and transfers the collateral into the market, so a correct deposit leaves the user's wrapper balance at zero and reads as failure.
