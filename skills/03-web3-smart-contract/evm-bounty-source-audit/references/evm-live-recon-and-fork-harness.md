# EVM live-target recon and fork harness

Companion to `templates/ForkPoC.t.sol`. Use once a single live protocol is chosen (see `references/target-screening.md`): § 0 first — pin which source revision each live contract actually runs (repo HEAD ≠ deployed is the common case); then (1) size it on-chain before investing days, (2) stand up a pinned-block fork harness that reproduces its real flows — the same harness later becomes the submission PoC and validates each lead before you write it up.

## 0. Deployed-revision pinning (repo HEAD is often NOT what runs)

Scope language like "the contracts in `src/` that are in use on mainnet" means the DEPLOYED build, not the release tag the docs claim. Establish the revision per ADDRESS before auditing:

- **Byte-compare, but mask the immutables.** Build the candidate revision, take the artifact's `deployedBytecode`, mask every byte range in `deployedBytecode.immutableReferences` (`{start,length}` — usually 32-byte slots) plus the CBOR metadata tail in BOTH codes, then diff. Unmasked diffs give false MISMATCH verdicts: artifacts store zeros in immutable slots while live code carries real addresses, and a naive "differing bytes must be zero in the artifact" heuristic mis-splits runs at coincidentally equal bytes. Zero diffs after masking = deployed == that source (modulo immutables) — the citable statement for the report.
- **Metadata CBOR layout** (last bytes of runtime code): final 2 bytes big-endian = metadata length; the map reads `a2 64 "ipfs" 58 22 12 20 <32-byte digest> 64 "solc" 43 <3 version bytes>`. Same digest = same source graph + settings. Digest mismatch with ZERO code-diff = metadata-only difference (paths/settings/graph) — the code is still identical; don't cite the digest, don't chase it. Do NOT plan on fetching the metadata JSON from IPFS: teams usually never pin it (every gateway 404s) — build candidate revisions and compare bytes instead.
- **Pin per FILE, not per repo.** `git fetch --unshallow` (cheap for small repos), then `git log --format="%h %ad %s" --date=short -- <file>`: a file with ONE history entry is deployed as that commit whatever the tag says; a file modified after the tag means the deployed build is a LATER commit. Read the CHANGELOG for "deployed separately / outside the release set" entries — those contracts come from main at commits that can predate OR postdate the tag, and a "deployed separately" file may be absent from the tag entirely (then HEAD's copy is the deployed one). Build each candidate revision in its own shallow clone (`git clone --depth 1 --branch <tag> <url> <dir>`), not worktrees; record the per-contract {tag|SHA} pin in the deliverable and re-verify right before submitting (main moves).
- **Ambiguous cases resolve by build, not by argument**: compile each plausible revision (release tag, each file's add-commit, HEAD) and let the masked diff say yes/no per candidate. State residual unknowns as "audited at <rev>; deployed confirmed <rev>" rather than staying silent.
- **Cheap fingerprints before full re-builds.** (a) When the explorer serves VERIFIED source, save it and `diff <(tr -d '\r' < verified.sol) <(tr -d '\r' < repo.sol)` — identical text pins the deployed build to that source file in seconds, with no solc run. A non-empty diff still needs the masked bytecode comparison below, since metadata and import paths can differ. (b) Selector presence: `cast sig "fnOnlyInRevisionX(...)"`, then search the hex of `eth_getCode` for that selector — one grep settles the tag-vs-HEAD question in seconds (a function that exists only at HEAD missing from the deployed bytecode proves the deployed build predates it). (c) Revert-string pins: hex-encode a distinctive `require` message from the candidate source (`python3 -c "print('No bad debt'.encode().hex())"`) and grep it in the runtime bytecode found above; finding ALL such strings confirms the source family without compiling. (d) Cross-RPC hash agreement: `cast code <addr> --rpc-url <rpc> | tr -d '\n' | sha256sum` on TWO independent RPCs; identical hashes prove the bytes you read are not one endpoint's cache artifact. (e) Read immutable getters directly (`cast call <addr> 'minDebt()(uint256)'`) and compare with the source constants — a cheap sanity pin that needs no artifact. Note: `cast call` can fail with "failed to retrieve chain ID from fork endpoint" on some RPCs while `cast code` works; try a second public endpoint rather than concluding the contract has no such getter.
- **A reverting `eth_call` does not prove a function is absent.** Access-controlled functions revert with empty data from an unauthorised caller, which looks identical to a missing selector. Before claiming a version changed or a dangerous entrypoint was removed, confirm against source/ABI and grep the deployed bytecode for the selector; then read the guard on the verified implementation (`assert msg.sender == governance`, role check) to classify the revert as access control. Cross-version conclusions built only on revert/no-revert invert easily.
- **Diamonds (EIP-2535) verify PER FACET, and facets can carry DIFFERENT revisions of a shared file.** Fetch each facet address's own explorer JSON (`/api/v2/smart-contracts/{facet}`) — the diamond's own response covers only the diamond core, and each facet's `additional_sources` carries its libraries. Locate a function's facet by matching its 4-byte selector (`cast sig`) against the loupe's `facets()((address,bytes4[])[])` selector lists. When plain HTTP to the explorer is Cloudflare-challenged, issue the API call as a same-origin `fetch()` from a browser tab already on that host (the challenge's clearance cookie applies; chunk long JSON in ~20k `slice(off, off+20000)` slices and stitch). A shared `file_path` (e.g. a config `C.sol`) can appear in MULTIPLE revisions across facets: hash every copy and keep ALL variants tagged with their source facet — a first-seen-wins merge silently kept a stale revision missing a config key that the newer facet's copy had.

- **The repo's own release record IS the pin set — length-compare first, then cluster the diffs.** The deploy config ships the whole upgrade batch: `protocol-config/<chainId>/releases/<version>.json` → `deployments[]` = {contract, address, CREATE|CREATE2} for every moved contract, and `multisig[]` labels (`AccessManager grantRole <ROLE> -> <contract>`) that cross-check the on-chain role events. `eth_getCode` per address and byte-LENGTH-compare against the local artifact's `deployedBytecode` — one cheap RPC sweep, only then byte-diff the matches. Interpret by CLUSTERING differing offsets: equal length + diffs confined to 20-byte runs (baked library/immutable addresses) and one ~31-32-byte tail cluster (metadata) = same revision; scattered diffs = different revision (re-pin before claiming anything). Artifact path keys on the source FILE (`out/<SourceFile>.sol/<Contract>.json`) — a contract-name lookup misses library artifacts and reads as a false "empty artifact".

## 1. Funds-at-risk sweep (size the target in minutes)

Do this before deep review: it drives go/no-go and it supplies the report's "funds at risk" numbers.

- Enumerate addresses from the repo's deploy config (e.g. `protocol-config/<chainId>/protocol-config.toml` plus per-module dirs), NOT from the docs. Deploy config is generated from the actual deployment; docs drift and lag — a docs table can even point at the wrong pool. Cross-check with docs only to catch omissions.
- Find the contract's first real holders from its own deployment artifacts,
  not a guessed calendar date. Read `transactionHash` from
  `deployments/<chain>/<Contract>.json`, `eth_getTransactionReceipt` it for the
  deployment block, then scan `eth_getLogs` FORWARD in <=50k-block chunks
  (publicnode rejects wider ranges) for the contract's `Deposit`/`Transfer`
  topic. Why: date-to-block estimates can be off by millions of blocks on fast
  L2s and silently return an empty holder set.
- Sweep the money tokens across EVERY protocol contract, not just the core/entry points: diamonds, their modules, escrow/claimer/fair-launch contracts, treasury, admin multisig. Real value often sits in an escrow or claim contract, not in the AMM you happened to be reading.
- The sweep is a matrix: tokens x contracts. Per cell: `cast call <token> "balanceOf(address)(uint256)" <contract> --rpc-url <rpc>`. Also read protocol-token `totalSupply()`, and pool `getReserves()` (read `token0()`/`token1()` first to know decimals/order) to derive prices: token price from the deepest pool ratio; LP held by staking is worth `stakedLP/totalLP x pool value`.
- Report BOTH nominal and liquid: an escrow holding 35M of a token whose only pool holds 1M nominally "has" the big number, but "extractable today" is pool-bounded. Severity text usually reads the nominal figure — give both, labeled.
- Find the protocol's OWN supply oracle and see which implementation is live (proxy impl slot / deploy config) before trusting "circulating" in quote math — the pricing formulas divide by it, so its exact definition (which balances are excluded) is part of your model.

## 2. Pinned-block fork harness

The ordering that works:

1. `cast block-number` → freeze it as a constant in the test. Numbers are only comparable within one block; a floating fork re-rolls balances between runs.
2. Fill addresses from the deploy config; `vm.createSelectFork(vm.envOr("FORK_RPC", ...), FORK_BLOCK)`; run with `FORK_RPC=... forge test --match-path "test/fork/*" -vv`.
3. Recon test first (read-only): supplies, vault balances, quotes, allocations, limiter/config state — log all of it; it is the baseline diff source for every later claim.
4. Execution tests next (deposit/withdraw/claim/retire paths with real assertions on balance AND supply deltas).
5. Exploit-shaped test last, with MAIN vs CONTROL arms (see the template's section 4).

Rules that save cycles:

- **Before trusting a failing fuzz suite, prove setUp wires every external dependency the entrypoint reads.** An upgradeable vault that calls a NAV/oracle view reverts on every deposit with the contract's "unset address" error when the harness never set that oracle; the suite reports zero runs per case, which reads like a broken contract but is a harness defect. Deploy a minimal view mock, grant the updater role, wire it in setUp, and only then interpret failures.
- **Bound generated inputs against the contract's guardrails, or relax those guardrails explicitly in setUp and record it.** Per-call caps, cooldowns and percentage limits can reject fuzzed amounts before the invariant code executes; a suite failing on `ExceedsPeriodRewardCap`/`RewardExceedsMaxDelta` is measuring configuration, not logic. Use admin setters plus baseline liquidity so generated sizes stay inside the cap, with a comment marking the deviation from production. Match handler parameter width to the domain: `bound(uint64 raw, 0.8e24, 1.2e24)` clamps every case to the upper bound because uint64 cannot reach 1e24, so the campaign explores one value. Setter validation is part of the guardrail: a zero cooldown may revert, so set 1 second rather than 0.
- **Exclude helper mocks from Foundry invariant targets.** Foundry treats contracts deployed in setUp as fuzz targets; a mock setter (e.g. `setPrice`) can drive the oracle to arbitrary values and break a price-based invariant. Call `excludeContract(address(mock))` (and the asset token) in setUp so only the intended handlers drive the run.
- **For a full-repo Foundry build, install only production npm deps and init submodules before compiling.** `npm install --no-save --ignore-scripts @openzeppelin/contracts@<v> @openzeppelin/contracts-upgradeable@<v>` plus `git submodule update --init --recursive --depth 1` resolves OZ remappings and `forge-std/Test.sol`; without forge-std, `forge build --offline` fails on test imports even though contracts compile. This avoids pulling the entire Hardhat devDependency tree into the audit clone. When npm rejects a monorepo manifest with `EUNSUPPORTEDPROTOCOL workspace:*`, install those packages in a scratch directory with its own minimal `package.json` and copy `node_modules` into the audit clone. Why: the workspace root is not a valid npm install target, but Foundry only needs the Solidity sources.
- **Standalone micro-harness beats cloning a giant scope repo.** When the
  in-scope Solidity is a handful of contracts inside a mobile/app monorepo, make
  a fresh minimal Foundry project: copy an existing `forge-std` into `lib/`,
  declare only the interfaces you call at file scope, set `src/test/libs` and
  `solc_version` in `foundry.toml`, then pin the fork from the CLI with
  `forge test --fork-url <rpc> --fork-block-number <block> -vv`. Call the DEPLOYED
  addresses directly instead of redeploying the protocol. Why: the monorepo's
  front-end toolchain and dependency tree are irrelevant to a fork probe, and a
  stale pinned checkout only adds build failures.
- **Minimal local interfaces at file scope.** Declare only the structs/functions you call; do not import repo interfaces into the test. Struct field ORDER is the ABI — copy it exactly from the repo's interface file. Self-contained tests survive repo churn and compile against any release.
- **Assert balances on the token the contract actually mints.** An upgradeable vault can itself be the ERC20 (wYLDS) while its `asset()` is a separate mock token; `claimRewards` mints the vault token, so checking the asset mock reads zero and looks like a failed claim. Locate the mint site before writing the balance assertion.
- **On an upgrade, test the grandfathered path and the new guard side by side.** Reproduce the migration boundary locally (fill epochs until a new cap starts, then exercise a pre-boundary epoch), and assert both arms: legacy bypasses the new guard, post-boundary enforces it. When the proxy is deployed with the new implementation from setUp, the override already enforces the NEW role before initializeV2 snapshots the boundary; grant that role to the setup actor before creating legacy epochs or the first legacy write fails AccessControlUnauthorizedAccount. Then grade reachability — seeding the legacy root/epoch through an admin role makes it privileged-role-reachable and informational under the usual grading clause, so record a verified negative instead of a finding.
- **A guard present in V1 but missing in V2 is a behaviour change, not automatically a bug.** Diff implementations for guards that disappeared, write the probe that would have reverted on V1 but succeeds on V2, and continue only when a NON-privileged actor can turn it into value movement. An `initializeV2` with no caller check is exploitable only while `_initialized` is below the reinitializer version — read that storage slot on the live proxy before claiming it.
- **When a fork call is denied by a composed guard, instrument the sub-guards before changing code.** Call each public view the guard composes (`availableBorrowLimit`, `isPriceStale`, `isBelowMinDebt`, etc.) from the caller context and log them; the failing conjunct is then known. Use the TWO-argument `vm.startPrank(a, a)` on the first attempt: the one-argument `vm.startPrank(a)` leaves `tx.origin` as the test contract, so guards comparing `msgSender == tx.origin` deny the call even though every other conjunct passes, and the denial reads like a logic bug. If the two-argument prank still fails, whitelist the actor through the live operator role (`vm.prank(<operator>); allow(actor)`) instead of fighting prank semantics. BEFORE shipping, remove any allowlist that was only added to unblock setup and re-run: a PoC that depends on a privileged setup step is weaker than one using the real EOA path, even when that step is a real governance call.
- **Approve the actual puller, derived by tracing — never guess.** Follow the entrypoint's transfer path: if the flow pulls the credit/asset from the user into the vault, the user approves the VAULT; if the core protocol pulls the payment from the caller on behalf of an external aggregator, the user approves the CORE protocol, not the aggregator. A wrong spender reverts in a way that looks like a logic bug and burns a debugging cycle.
- **Assert quote == execution.** For any entrypoint with a view quote: read the quote, then execute the same size in the same block with a permissive min-out, and assert outputs are equal. A mismatch is either a finding or a units bug — make it loud.
- **Probe dead/live paths via try/catch.** Wrap a quote/entrypoint in `try ... catch (bytes memory err)`, log `bytes4(err)`, and resolve it immediately with `cast 4byte 0x<selector>`; fall back to trying `cast sig "<ErrorName(uint256)>"` for candidate errors from the repo's Errors.sol only when 4byte has no match. The name tells you which guard fired without re-reading the whole call graph.
- **Discover state you cannot view: probe with minimal STATEFUL calls.** When no getter lists which (id, scope) pairs hold value (e.g. per-lock allocations across classes) and a dead/stale subgraph makes log-scanning useless, probe instead: call the smallest mutating op (`deallocate(id, scope, 1e18)`) per pair in try/catch — success marks a live pair, revert marks absent. Then measure magnitudes from AGGREGATE getter deltas (total allocation per scope) around the real drain, halving the amount when a full-size call reverts on a residual-balance guard. Record each key's drained amount and REPLAY exactly those deltas for any restore/undo leg — re-running the halving probe upward overshoots into spare capacity (principal − allocated headroom) and an exact-restore assert then fails by the overshoot. A revert selector UNIFORM across every probed key means a key-level storage artifact (per-key maps already empty/cleaned on a closed object), not per-key state: stop probing sibling keys, check the object lifecycle, and do not carry a gate-missing lead into the report until at least one live object actually takes the path.
- **Empirical trust probe for a closed-source callee.** When the contract whose validation you must judge has no source (unverified facet, docs-only partner), test on the fork in ARMS: (A) correct parameters → expect success AND record the exact charge/output (this pins the price formula to the wei); (B) heavy manipulation (price = 1); (C) partial manipulation (half price). All wrong arms reverting with the SAME selector while A fills at exactly the stated price = the validation exists (Klima RA→Carbonmark `fillListing`: docs claimed "fill at unitPrice or it reverts", the arms proved it — a corrected read that CLOSES a lead, which is a valid outcome). A wrong arm succeeding, or taking a visibly different path, is a candidate finding — escalate to a measurement PoC. Docs statements about validation are a hypothesis; the arms are the evidence.
- **Reproduce the pricing math in python before trusting a "weird" quote.** Compute the code's formula by hand for 1 unit and compare with the on-chain quote. One match converts suspicion into a validated model of the curve; the model is then your manipulation-planning tool.
- **EIP-55 checksum is required for address literals in Solidity**, even when the deploy config stores lowercase. `cast to-check-sum-address 0x...` each one; compiler error 9429 also prints the corrected form. (Alternative: load addresses from JSON/TOML at runtime via `vm.parseJsonAddress`.) Wrapping the literal in `vm.addr(uint160(0x...))` does NOT bypass the check — solc still parses the inner hex as an address-like literal and reports error 9429. Batch-convert every literal with a Python loop calling `cast to-check-sum-address` before recompiling. Also avoid `view` as a local variable name in generated harnesses: it is a reserved keyword and produces a confusing "state mutability can only be specified for address types" error at the declaration.
- **Handlers that need a live allowlist/KYC gate (whenVerified-style): mock the check from live config, don't hunt for a verified actor.** Read the gate's config getters off the target (cooperator + verifier addresses), then `vm.mockCall(verifier, abi.encodeWithSelector(checkSelector, cooperator, actor), abi.encode(true))` per actor at handler construction, and prove in the smoke test that each op class executed (counters > 0) before trusting a campaign. Check the per-entrypoint modifier set while you are there — the one op that SKIPS the gate is where a finding can live (one protocol's allocate/reallocate required KYC while deallocate — the only allocation-reducing path — did not).
- Fund test users with `deal(token, user, amt)` and IMMEDIATELY `assertEq(balanceOf(user), amt)` — exotic ERC20s store balances non-standardly and deal can silently miss. Fallback: impersonate a real holder (`vm.prank`) or raw `vm.store`.
- **Fork-based invariant campaigns are cold-start-bound.** Every campaign RUN re-selects the fork, so cost ≈ runs × (cold fetch + depth × ~1s per cold call): a measured 32×60 campaign (1,920 calls) took 505 s on a warm-ish cache, while re-runs ride Foundry's on-disk RPC cache and are far cheaper — scale coverage by warming the cache and re-running, and reserve multi-million-call budgets for the box. Prefer invariants that need no ghost bookkeeping where possible: exact conservation (aggregate == baseline + recorded signed deltas per op) is the sharpest allocator invariant, and the smoke test's per-op counters are what prove each op class actually executed before the campaign result means anything.
- **Authorized addresses can be uninitialized shared implementations, not the live instance.** Symptom: every getter returns zero and a decimals-style call reverts `0x` while `eth_getCode` is non-empty. Enumerate the deploying factory's `deploymentsLength()` / `deployments(i)` array, then read the instance's EIP-1167 bytecode (`363d3d...73<impl>5af4...`) to prove which authorized implementation it delegates to before fuzzing state. Run the scope guard on the clone addresses too: if they are not separately listed, record `authorized: false` explicitly rather than silently treating the clone as in scope.
- **Keep handler token accounting signed.** When one handler op both delivers tokens into the contract and pays them out (e.g. harvest-then-withdraw), `balanceAfter - balanceBefore` is negative whenever payout exceeds simultaneous delivery; an unsigned subtraction panics `0x11`. Use `int256(after) - int256(before)`, accumulate only positive delivery deltas, and compare invariants against signed expected values.
- **A reward-payment metric stuck at zero often means no time passed, not a broken contract.** Lender/local-reserve revenue accrues with `block.timestamp`; a same-block `distribute()` may move nothing after the first call. Add `vm.warp(block.timestamp + 1 days)` immediately before the distribution-triggering handler op and re-check the counter before trusting a zero. Record the warp as synthetic environment input in the ledger.

### Vyper targets: compile outside Foundry and clone the original

When the pinned scope is Vyper and Foundry cannot select the pinned compiler, do not spend cycles on config keys: compile the `.vy` sources with that exact `vyper` CLI into creation bytecode and deploy from the Solidity test.

- Keep the `.vy` files OUT of `src/` (for example under `bytecode/`) so `forge build` never tries to compile them; declare only the Solidity interfaces you call.
- `PYTHONWARNINGS=ignore <vyper-cli>/vyper.exe -f bytecode <file>.vy > <file>.hex 2><file>.err`, then strip the trailing newline. Why: an older Vyper emits Python deprecation warnings on stderr and Foundry treats compiler stderr as a failed build.
- In the test, `vm.readFile` the hex, normalise a missing `0x` prefix, `vm.parseBytes`, then `assembly { addr := create(0, add(code, 0x20), mload(code)) }`. This runs the constructor, unlike `vm.etch`.
- To clone a Vyper original whose `initialize` asserts `asset == 0` because the constructor sets `asset = self`, deploy a minimal proxy with the FULL EIP-1167 creation bytecode: `3d602d80600a3d3981f3` + runtime `363d3d373d3d3d363d73<20-byte impl>5af43d82803e903d91602b57fd5bf3`. Deploying only the runtime tail makes `create` return address(0).
- Run the same harness with and without `--fork-url`; the fork run costs seconds and proves the assertions do not depend on local EVM defaults.

Vault redeem harnesses: model losses that stay in the strategy. Conservation is `idle + debt <= real assets - trapped`, not equality. `trapped` is asset physically left in a strategy after it under-delivers; equality without subtracting it produces a false finding. When a strategy returns MORE than recorded debt, the surplus stays in the vault token balance but is never added to idle, so assert `accounted <= real - trapped` and quantify the surplus explicitly. A scenario where a strategy over-returns needs an unreported gain or a third-party strategy bug; mark it informational unless a non-privileged actor can both create the condition and capture the surplus.

## 3. cast-output pitfalls (cost a full false-alarm cycle once)

- `cast call` prints big uint256 as `value [annotation]` (e.g. `4221628222436031 [4.221e15]`). Parsing the whole line as int or hex silently yields None/0 → a wholesale "all balances zero" false conclusion. Parse the FIRST whitespace token; before believing a zero sweep, print one known-nonzero balance raw.
- Multi-return calls (e.g. `getReserves()`) print one line per value — split lines, take each line's first token.
- Struct returns without a full tuple signature print as flat hex words. Either supply the full tuple signature or, inside a Foundry test, call typed through a local interface.
- Batch sweeps in one bash loop with a tiny sleep and one retry; public RPCs throttle long loops. A JSON-RPC batch can answer HTTP 200 with only a subset of the requested ids, so parse responses by id and retry missing ones individually instead of treating the response as complete. Some addresses are not what they claim (an old pool can revert `getReserves`) — tolerate per-cell errors, don't abort the sweep.

## 4. Ops gotchas (Hermes + Windows/git-bash host)

- When Foundry `vm.ffi` runs `bash -c "cast ..."` and the child reports `cast: command not found` while `cast --version` works in your own shell, the child is a different bash (WSL-style paths under git-bash). Put a tiny executable named `cast` on that child's PATH (e.g. `~/bin/cast`) whose only line execs the native `cast.exe` through its `/mnt/c/...` path; keep the real Foundry bin directory on your own PATH too. Why: project test setup calls `cast` through `vm.ffi`, so a working parent shell does not prove the test harness can see the binary.
- When a repository's Foundry suite calls a Go-built FFI helper through `vm.ffi` with a relative path such as `./scripts/go-ffi/go-ffi`, a missing helper makes whole test files report failures that are harness gaps, not code defects. Build it from the pinned source with the Go version declared in that helper's `go.mod`, using `go build -buildvcs=false -o <name>.exe .` when VCS stamping fails because the host's git executable cannot be invoked; place the binary at the exact relative path the tests call, then re-run the suite before recording any verdict. Why: a reviewer can otherwise report a dozen failing tests that all pass once the helper exists.
- `forge test` accepts only one `--match-path` per invocation. Loop over files in the shell or pass a single glob; a repeated flag aborts immediately with an argument error, so a campaign that looks run produced no results at all. `--match-contract` has the same one-flag limit but takes a regex, so `'SuiteA|SuiteB'` runs both suites in one invocation.
- Verify an operator-provided credential at the exact path the tool reads before relying on it: check the file exists and is non-empty, and normalize by reading its bytes into the expected `.env` without printing the value. A Save As dialog can put the key into the FILENAME instead of the file body. Why: a mis-saved key silently fails every authenticated call, and debugging the tool instead of the file wastes a cycle.
- `write_file` refuses to overwrite an existing file it has not seen in full — a partial read does not clear it, and any intervening `patch` re-invalidates eligibility; it can even refuse right after a full read. Don't fight it: iterate with `patch`, or rewrite under a fresh filename.
- You cannot `mv`/`rename` a directory while the persistent shell's cwd is inside it (Windows lock, `Permission denied`). `cd` out first, then move.
- A bash `while read -r` loop over a Windows-produced file (python output, repo JSON) carries a trailing CR into the last field — native CLIs then fail on every iteration (`cast: odd number of digits`) while the loop "runs"; `tr -d '\r'` the file (or have python write with `newline='\n'`) before feeding values to native tools.

## 5. Rate-limiter / "effective value" pricing asymmetry

When a price divides by (or scales with) a controlled aggregate — allocations, deposits, TVL, shares — and only ONE direction of that aggregate is rate-limited, the pairing is the finding class:

- **Prove the limiter is actually enabled before treating its edge as live risk.** Enumerate every in-scope asset from the protocol's own markets API, then batch `eth_call` the enable flag (`isRateLimited(address)`) and the price/config it consumes (`tokenPrice(address)`) across all of them. If the flag is false everywhere, a PoC that demonstrates the edge is a DESIGN DEMO, not a finding: record the counts and retract the live-risk claim in every artifact that carried it. Why: a hook guarded by `if (!isRateLimited[msg.sender]) return;` is inert, and a reviewer who checks one `eth_call` will discard a submission that implies current exposure. A governance-configurable feature can become live later; say that explicitly instead of implying present danger.
- **Map every mutation of the aggregate per direction.** Which entry points can DECREASE it (withdraw/deallocate/claim/expiry) and which can INCREASE it, then check the limiter (or its absence) for each. An instant-down path beside a ramp-up path lets a large holder collapse the pricing denominator in one tx (Klima: `allocate` was rate-limited, `deallocate` was not → retirement price fell ~4x after a 76% deallocation).
- **Check both orderings and every reader of the aggregate.** Some paths price off the raw aggregate while others price off a rate-limited "effective" copy (Klima: swap-in used effective, retire used raw). Compute the protocol's own formula in python against live reads (§2's reproduce-the-math rule) and compare per-path output: a cost/out ratio CONSTANT across sizes means no size-dependent arbitrage tier; a spread on one direction only is the window.
- **Quantify required dominance, then look for attacker-free windows.** Compute each holder's share of the aggregate from the probe map above; state the honest trigger set — an entity controlling enough of it OR a PREDICTABLE cohort event (maturity/epoch expiry moves the aggregate with no attacker at all). Report the "any user can act cheaply during the window" version alongside the "dominant holder" version; the second alone reads as unreachable.
- **Grade severity from the whole constraint chain, not one module's constants, and restructure the position before accepting an extreme precondition.** A finding in a slashing/insurance path can be gated by thresholds in DIFFERENT contracts (e.g. a borrow controller's `minDebts[market]` versus a slasher's `maxCollateralValue`). Re-read every gate from chain, derive the required precondition algebraically, and try to relax it with an attacker-controlled variable (position size, repayment, repeated `withdrawMax`) before grading — a naive max loan can need a ~98% dip while a shrunken position needs only `low/high < CF²` (see §8). Live-reachable plus an extreme precondition is Medium, not Critical; live-reachable with a realistic precondition changes the grade. Put the derived bound in the report so the grading is auditable. A reviewer's quoted defaults are not live config — re-read each threshold yourself before writing the finding up.
- **Price the counterfactual with the protocol's own function, not arithmetic.** To quantify "paid X, should have paid Y for the same output", binary-search the protocol's monotone quote entrypoint for the EXACT same output amount on the unmanipulated state (~16-18 view calls) and cite that figure; scaling an average price by tonnage is off by the curve's curvature (~1% on a quadratic-denominator formula) and a reviewer's recomputation will flag it as an approximation. After second-opinion review, re-derive every reviewer-touched figure (exact fair cost, exact discount %) and make their corrected numbers canonical in the write-up.

## 6. Privileged-role inventory (access-manager deployments; feeds the report's honest bounds)

Do this BEFORE writing any "requires privileged access" exclusion note — the exact holder set decides it.

- **On a local fork, read roles with `hasRole(roleHash, address)`; do not call `getRoleMemberCount` on plain OZ `AccessControl`.** That getter belongs to `AccessControlEnumerable` and reverts with an empty response on `AccessControl`, which looks like an RPC failure. Take each hash from the contract's own `ROLE()` getter (`cast call <proxy> "REDEEM_OPERATOR_ROLE()(bytes32)"`) rather than a hand-computed keccak, then probe every address from the repo's deployment JSON. Treat a JSON-versus-fork mismatch as stale configuration until grant/revoke events are traced; roles are routinely transferred after an upgrade, so a stale role table alone is not a finding.
- Pull ALL logs of the access-manager contract via Blockscout v1 (`/api?module=logs&action=getLogs&address=<am>&fromBlock=0&toBlock=latest&page=1&offset=1000`), same-origin from a browser tab when plain HTTP is Cloudflare-challenged. Do NOT pre-filter by a hand-computed `topic0`: a wrong-signature guess returns "No logs found" and fakes an event that never fired — deployed AccessManager builds differ in event parameter layout even when the name matches. Histogram topic0 over the full log set and work from what exists.
- When the hosted RPC's `eth_getLogs` is archive-gated, fall back to Blockscout v2 `/api/v2/addresses/<contract>/logs`: follow `next_page_params` until the range covers the upgrade, append every page to a JSON file before filtering, and use the `decoded.parameters` array on each item. This traces role grants/revokes without hand-decoding topics and survives a flaky single request because saved pages are not re-fetched.
- Decode grants as (topic1 = roleId, topic2 = account) and subtract revokes for the CURRENT holder set; classify each holder via `/api/v2/addresses/{addr}` (`name`, `is_verified`, `proxy_type`, `implementations`) to split Safes/system contracts from EOAs — a deployer EOA commonly keeps one operational role after its admin roles are revoked, and that single EOA is the trust story the report must state plainly. Do NOT infer Safe from code size: TimelockController, SafeProxy and ordinary contracts all carry runtime code. Fetch `/api/v2/smart-contracts/{addr}` and read `name`; a small `SafeProxy` answers `getThreshold()`/`getOwners()`, while a TimelockController answers `getMinDelay()` and has non-enumerable roles. Probe `hasRole` for known candidates and record when EXECUTOR_ROLE is held by address(0) — anyone can execute once the delay elapses.
- Map roleIds onto the repo's role-constant library (a `...RoleLib.sol` of `uint64 constant` ids) before writing bounds; record the final holder table as a JSON artifact next to the notes so every cited number has a file.

## 7. Sweep set for the "have you used all the tools?" pass

The cheap set that usually closes a code-audited target with evidence or upgrades the verdict in one pass:

- Full slither pass, `lib/` noise filtered. 0.11 logs group results as `Detector: <name>` blocks — histogram those for the inventory; there are no `Impact:` lines. Treat `dead-code` as a REACHABILITY lead, not noise: grep every call site — when an internal helper is the ONLY caller of a role-gated maintenance entrypoint, that entrypoint is uncallable in production; confirm against the pinned deployed build, then re-check any exploit story whose trigger was that dead path (an "expiry window" hypothesis dies when the cleanup it waited for never runs).
- EVMole over every in-scope unverified bytecode: its argument inference labels every word-sized parameter `uint256` (bytes32 indistinguishable) — confirm exact signatures by calling the function or resolving via 4byte before claiming a selector map; 4byte.directory's API 403s without a browser User-Agent header.
- Blockscout event/config forensics (role inventory: §6) plus a deployed-vs-repo pin from the repo's own release records (§0).
- Prove permissioned reachability by enumerating the whitelist, not by assuming it: sweep the setter events across ALL deployed versions of the contract (Blockscout search by contract name returns every version), then probe the getter for each candidate address found in docs or integrations. Zero setter events plus false getters means the allowlist is empty and the path is closed; record the addresses and observed values as a negative instead of filing a hardening item. Why: a getter cannot enumerate a mapping, and an empty allowlist is the common reason an unsafe primitive has no on-chain exploit path.

## 8. Hand-built custom EIP-2718 transactions for PoC

When `cast send` cannot emit the in-scope transaction type, build the raw EIP-2718 bytes in Python and submit through `eth_sendRawTransaction`.

- Read the field order and signature domains from the pinned source (`rlp_encode_fields`, `SENDER_SIGNATURE_TYPE`, `PAYER_SIGNATURE_TYPE`, `REPLAY_ID_TYPE`) instead of guessing from a spec summary. Encode ints as minimal big-endian RLP, addresses as 20-byte strings, `None` as the empty string, and open payer as the single byte `0x00`.
- Sign the raw 32-byte digest with `cast wallet sign --no-hash --private-key <key> 0x<hash>`. Without `--no-hash`, Foundry applies the EIP-191 prefix, the node recovers a different sender, and the failure surfaces as `have 0` on a funded account, a misleading balance error rather than a signature error. `cast keccak <prefix||rlp>` (raw hex, no `0x` prefix) is enough for hashing when no keccak library is installed. Assert the signature is 65 bytes with `v` in {27,28} before submitting.
- For a sponsored transaction the payer hash substitutes the resolved sender into the sender slot: encode the body with the wire sender empty, but compute the payer hash with the address filled in.
- Fee fields sit outside `replay_id` by design. To test nonce-free replay, send two transactions with identical `replay_id` and different `max_fee`; one is accepted and the other rejected with `nonce-free replay detected`. Do not report seconds-versus-milliseconds representations yielding distinct replay ids: binding to the raw field is intentional.
- Validate the shape from the receipt before trusting the result: `type` must be the custom type byte, `payer` must be the sponsor, and `gasUsed` must equal `gas_limit` for self-pay or `gas_limit + payer_auth_cost` for sponsored. Deposit-type receipts stay metered.
- `cast send <to> 1wei` is parsed as a function signature and fails with `Function signature does not contain parentheses`; pass `--value 1` with no positional data argument.

## 9. Pessimistic-oracle (daily-low) fork tests

When collateral is valued through a dampened "two-day low" oracle, these mechanics dominate both PoC construction and severity grading:

- **Measure an EMA feed's reachability before citing a one-block bound.** Read the time constant (`ma_exp_time` or equivalent). With `alpha = exp(-dt/tau)`, one block moves the EMA only by `(1-alpha) * (last_price - ema)`, so a 90% one-block jump in `last_price` can leave `price_oracle()` unchanged. Fork test both swap directions to find the one that LOWERS the price, then loop `vm.warp(now + 60)` with bounded swaps, logging EMA drop in bps and accumulating `dx` spent and `dy` received. Size `dx` so total `dy` stays below the pool's output reserve. Report net cost `dx * initial_price - dy`, converted to USD with the native-token feed, not gross notional. Why: an unchanged EMA in one block is not evidence of safety; sustained reachability and its cost are the citable facts.
- **Clear the daily-low mapping to isolate the EMA's effect.** When a manipulated feed price does not reach `viewPrice`, compute the nested mapping slots from the oracle's storage layout (`keccak256(abi.encode(key, slot))` twice), `vm.load` to confirm the recorded low, then `vm.store` zero for today and yesterday and rerun. If the drop propagates only after clearing, the dampening window is the binding constraint, not the feed. Why: otherwise you blame the feed for a guard that is doing its job.
- **Quantify against real borrower positions before claiming impact.** Enumerate borrowers from `Borrow`/`Repay`/`Liquidate` logs via the explorer address-logs endpoint, reconcile net debt against `totalDebt()`, and compute the price drop needed to cross the liquidation or bad-debt threshold. A 30% price drop can still leave every position healthy. Why: a large percentage move is not automatically a funds-loss path.

- **Reset today's low before any position restructuring.** `viewPrice` is a pure read, but `getPrice` writes `dailyLows[token][day]`, and withdrawal/borrow limit helpers call `getPrice` internally. On a fork whose current day already holds a recorded low, `withdrawMax` loops converge short of the intended size and the precondition looks worse than it is. Under a mocked feed, call `getPrice(token, cf)` once at the high price FIRST, then shrink. Why: the hidden write dampens every later limit, so a clean-looking loop silently mis-sizes the position.
- **Derive the minimum precondition algebraically, then restructure the position.** For a slash that nets `debt - viewPrice·collateral` under a borrow-side `minDebt` and a slash-side `maxCollateralValue`, a fresh max loan needs a deep dip. Instead: borrow the minimum allowed, repay down to just above the slasher's `minDebt`, then `withdrawMax` repeatedly until collateral ≈ debt/CF. The required dip collapses to `low/high < CF²` because `pessCV = debt·(low/high)/CF²` at that size (CF 0.85 → ~27.75%, CF 0.92 → ~15.4%, versus ~98% unshrunk). Why: the ratio between the two contracts' thresholds, not either alone, sets the real precondition, and position size is attacker-controlled.
- **Survey feed manipulability before claiming a flash-loan oracle manipulation.** Classify every in-scope feed: Chainlink aggregator (not trade-movable), Curve `price_oracle` EMA (movable but bounded per block), `get_virtual_price`/`pricePerShare` (donation raises, not lowers), and feeds with a hard floor (the floor may block the dip entirely). Check the required dip against each market's CF² before promising a real-trade PoC. If no feed can move enough in one block, state that in the report and use `vm.mockCall` on the feed — the program explicitly allows oracle manipulation as a precondition. Why: an unachievable real-manipulation claim invites dismissal, while a clearly labelled simulation of an allowed precondition keeps the code bug in scope.
- **Prove "no genuine bad debt" with both valuations.** Log true collateral value AND the dampened value at the moment of the payout; an overpay on a position solvent at the true price is the harm, while an overpay on a genuinely insolvent position is only a valuation dispute. Why: the two cases have different severity and the team will argue the latter.

## 10. Live borrower sweep and callback-liquidation fork harness

### Enumerate real borrowers without archive `eth_getLogs`

When public RPCs cap `eth_getLogs` to a tiny window, use the explorer's Etherscan-compatible logs endpoint on the chain instance:
`GET https://eth.blockscout.com/api?module=logs&action=getLogs&fromBlock=0&toBlock=latest&address=<protocol>&topic0=<sig>&topic1=<marketId>&topic0_1_opr=and`.
- Pass `topic0_1_opr=and` whenever both `topic0` and `topic1` are supplied; without it the endpoint returns 400 `Required query parameters missing`, which reads like an unsupported API rather than a missing parameter.
- Derive `topic0` from the event declaration in the pinned source with `cast sig-event 'SupplyCollateral(bytes32,address,address,uint256)'` (and `Borrow(...)`, `Liquidate(...)`). Guess the event name or the indexed-parameter layout and the query returns "No logs found", faking zero borrowers.
- Collect the address words from topics 2+ of `Borrow` and `SupplyCollateral`, dedupe, then read `position(id, user)` for each with `eth_call`. Compute debt from `borrowShares * totalBorrowAssets / totalBorrowShares` and compare `collateralValue * 1e18` with `debt * lltv`. A positive margin on every borrower is a VERIFIED NEGATIVE for "an underwater position exists now", not a reason to claim liquidation code is safe in general. Record the price, market totals, LLTV, per-borrower margin and log counts as the evidence artifact.

### Drive a callback-based liquidation to the success path

For protocols whose liquidation helper relies on a `onMorphoLiquidate`-style callback (live helper → live protocol → live wrapper):
- Read the market params from the protocol itself (`idToMarketParams(id)`) and confirm `collateralToken` is the expected wrapper before building the harness.
- Use the wrapper's REAL `depositAssets(amount, receiver)` path. It commonly pulls the underlying, wraps it AND supplies the wrapper as collateral to the lending protocol in one call. After it returns, assert the protocol `position(...).collateral > 0` instead of asserting the borrower's wrapper `balanceOf` — the borrower may never hold the wrapper; the protocol does.
- Morpho-style `liquidate` enforces `exactlyOneZero(seizedAssets, repaidShares)`. Passing both amounts, or both sentinels, reverts `inconsistent input`. Set `seizedAssets > 0, repaidShares = 0` (or the reverse) and let the protocol derive the other side. Fetch upstream source to confirm this guard whenever a liquidation harness fails at the protocol entrypoint.
- Private checkpoint structs have no public getter. Find the slot with `forge inspect <Contract>:<Name> storage`, then `vm.load(contract, keccak256(abi.encode(user, uint256(slot))))` and take the first word as `balance`. A call to a nonexistent getter reverts with empty data and looks like a broken harness.
- A multi-step harness that calls live protocol, module and wrapper often overflows the stack at the outer call. Set `via_ir = true` in `foundry.toml` (with optimizer on) before hand-shrinking the test; it resolves the compiler error without changing the code under test.
- Give the callback helper enough loan token inside the fork to cover `repaidAssets`, pass empty swap calldata (`abi.encode(new bytes[](0))`) when no swap is needed, and assert the helper ends with zero loan-token balance — that is the no-residual-funds invariant for a stateless helper.
- Bound fuzz parameters to the protocol's health band: borrow below the initial LLTV-derived max, then mock a price low enough to make the position unhealthy. With `priceFactor`, `collateralAmount` and `seizeBps` as fuzz inputs, assert exact deltas for victim checkpoint, wrapper supply, liquidator unwrapped shares and helper loan balance. A deterministic success run plus a bounded fuzz over the same path is the evidence shape; a campaign where every case reverts only proves the revert side and must be labelled that way.
