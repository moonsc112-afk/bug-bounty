# Smart-contract bug-bounty audit (EVM + Solana)

Rules that keep the cluster from forking:
- The procedure, tooling, PATH traps and reporting conventions here are authoritative. A spoke never overrides them, and its kill signals (e.g. `web3-audit` TVL < $500K) are advisory: `bounty-target-verdicts` and the live program page win.
- Do not run two spoke checklists in parallel on the same code. Pick the spoke matching the target class, take its list, then return here.
- Verdicts and prior negatives live in `bounty-target-verdicts`, not in any spoke.
- Phase routing across a whole engagement is `bounty-hunt-pipeline` (P0 to P6); coverage across empty classes is `redteam-mindset`.

Audit workflow: acquire source, static audit, fuzzing. EVM = Foundry, Solana = Rust/Anchor in WSL. ## How to work the task (user preference)
- When the operator names a target with uncertain spelling, inventory local artifacts under near-miss spellings before summarizing; do not answer for the first alphabetic near-match. Why: another agent's similarly named report can be unrelated, and a confident wrong-target answer wastes the turn.
- When cross-checking inherited audit work against a supplied engagement bundle, follow `references/competition-audit-acquisition.md` section 6: set-diff the file list against `scope.json`, query `statements.json` known issues before any PoC, and prove a mock harness is wired to the real ABI before citing its results.
- Sequential, one impact per hypothesis. Ref: `references/agent-led-verification-pipeline.md`.
- In invariant fuzz tests assert the direct state invariants, not a closed-form approximation whose inputs depend on fork state (prior-day lows, cached oracle values): the approximation breaks on a shard you did not run even while the invariant holds.
- Before posting to Mantis, follow references/mantis-submission.md: show the operator the complete paste-ready draft and submit only after explicit approval.
- When the operator answers an options menu with several numbers or letters, execute every selected item to completion in that turn before replying; do not stop after the first one.
- When a potential bug surfaces, STOP breadth and dig that lead deeper (trace the handler + access control, build a focused PoC/fuzz) before moving on.
- Report honest negative results plainly and recommend the next-best-odds target; never invent a finding to show progress. When a measurement FALSIFIES one of your own earlier claims, rewrite every artifact that carried it (draft, report body, summary-table row) with the measured behaviour and say which claim is retracted — a hypothesis a targeted PoC killed must not survive in a delivered file, and a reviewer who re-tests the claim will use your own numbers.
- Attribute a severity or reachability cap to the EXACT quantity a config parameter bounds, not a nearby quantity: read the subtraction/condition that consumes it before writing the bound. A cap on collateral VALUE (`maxCollateralValue`) does not cap a payout computed as `debt - collateralValue` — a fuzz sweep found a 5x larger payout than a draft that capped it at the parameter. Re-derive every 'bounded by N' sentence from the formula before it ships.
- A target close-out (the operator says "don't force it" / the verdict is zero payout-grade findings) = a compact coverage ledger: what was swept, verdict per lane, what stays open (disclosures, monitors). Then stop; no padded side-quests.
- Before resuming a target the operator names, read its `findings/engagement-status.md` and `submission-receipt.md` first. A P6 close-out with a terminal duplicate ruling is a closed target: report the receipt and stop, do not reopen the root cause. Why: the prior ledger already carries the ruling, and re-litigating it spends the session without changing the payout outcome.
- A "zero findings / stop the loop" verdict from your OWN session is INVALID
  until you inventory `E:/audit/*/findings/` and parallel agents' reports/PDFs
  first. Read any S*.md / *.pdf BEFORE any defeatist conclusion, then advance
  that finding instead of re-auditing fresh targets. WHY: a parallel session
  may already have proven a submission-ready finding this session never saw.
- Treat a prior KILL verdict in a coverage ledger or an earlier session's note as a CLAIM, not a fact: re-read the artifact that produced it and confirm the observed error maps to the claimed cause before relying on it. A wrong hand-encoded discriminator can manufacture `InstructionFallbackNotFound` and fake a "not deployed" kill, which then gets copied into reports and checklists. WHY: closing a live surface on a harness error hides the only reachable path and makes later sessions re-verify the wrong thing.
- For status questions ("what's left / what haven't you worked on"), inventory ALL agents' artifacts on the machine before answering — the user counts every agent's output as "your work". A clone directory proves source acquisition, not an audit, and a parallel session may be mid-audit right now. Cross-reference procedure + per-agent artifact map: references/local-arsenal.md § Progress status cross-reference.
- Deliver finding reports to the operator in INDONESIAN as a PDF (pdf skill) BEFORE executing numbered follow-up action steps; keep the submission-ready draft in English. The operator reads Indonesian, bounty platforms read English. Avoid em-dash in Indonesian reports; use comma or colon instead.
- Say what a side quest BUYS, in one line, when proposing it or handing it over: the operator will ask 'what is that for?'. Name the finding/payout path it unlocks (e.g. a verification request unlocks the only unaudited surface = new candidate findings there) and state plainly when it produces no payout by itself. Corollary: the payout path never blocks on a side quest — submit the findings that are already ready regardless of whether the request lands.
- When the operator asks whether the full arsenal was used ('have you used all the skills, like rea?'), answer with a per-tool inventory — used / not used + the reason — and actually RUN the cheap unused items that fit instead of leaving listed capabilities untouched. 'No applicable target' is a valid answer only when you can name the target class it would need (e.g. a closed-source binary for REA) and say which alternative covers the gap. Apply the same shape when proposing to CLOSE a target: enumerate the remaining un-audited SURFACES (in-scope assets never swept, harnesses never run, scope entries never classified) with an honest payout probability per item, and take a 'so you gave up?' pushback as an instruction to execute the cheapest decisive remaining check — not to re-argue the verdict. A single tool/config sweep that was never run is the usual answer, and it either closes the target with evidence or upgrades the verdict in one pass. Usual sweep set: references/evm-live-recon-and-fork-harness.md §7.
- Within ONE target's hunt the tracks run in PARALLEL — coverage expansion (multichain scans as background jobs), invariant fuzz, second-opinion reviewers — while target-level focus stays sequential (the rule above is about choosing targets, not about these workstreams). "Keep going until you find a bug" authorizes exactly that multi-track hunt; checkpoint status between tracks instead of finishing one track to a summary first. Give each parallel workstream its own artifact directory under `findings/` and require the same compact result schema (summary, artifact_paths, candidate_findings, negatives, blockers, next_steps) in a `result.json`. WHY: disjoint directories stop sibling agents clobbering each other's deliverables, and a shared schema lets the parent aggregate verified claims without mining transcripts.
- Second-opinion reviews run as parallel READ-ONLY subagents, each with a distinct lens — per-contract adversarial review, core↔extension seam review, deprecated-vs-current regression diff — and each gets an explicit EXCLUDE list (one line per already-reported finding, root-cause level) plus a JSON output schema (`file:line`, mechanism, impact, confidence, why-not-already-known, poc_sketch). Tell them NOT to run `forge build`/`forge test` in the shared repo — parallel builds collide; static reads only. Their findings are CLAIMS to reproduce, not results. When a reviewer fails or times out (rate limit, upstream 429), its lens is NOT covered — take that lens over yourself or re-dispatch after the limit resets; never count a failed subagent as a negative result for its area, and say plainly in the handoff which lenses were actually reviewed.
- Check `scripts/` + `references/` before hand-writing tooling — email sender, report builder, fleet scan ship as scripts to adapt. For a fork-versus-upstream source comparison, run `scripts/function_diff.py <upstream.sol> <fork.sol>`: it strips comments, brace-matches each function body, and prints a SAME/DIFF table so only the fork's own edits need manual review. Do not reimplement that brace-matching extractor in an ad hoc Python script: the shipped script already normalizes comments and whitespace, while a hand-rolled version silently returns empty bodies for functions it fails to match and reads as a clean differential.
- When UPDATING an already-delivered report built from a spec/element list, splice by matching the section's own boundaries and then diff the section-heading list before vs after the rebuild — range-based index splicing over element arrays silently drops boundary sections (replacing two adjacent index ranges deleted the section between them until the heading list was re-checked). A parallel agent session may be editing the SAME report file: before writing, re-read the heading sequence AND scan the rows for claims you did not write — they will contradict your own conclusions (a shared report carried "increase orders can never execute" while the code showed the opposite). Reconcile instead of clobbering: patch the wrong claim in place and cite the evidence, renumber so there is exactly ONE linear section sequence, sync the cross-references (summary-table row ranges, `§N` pointers), then tell the operator what changed.

## Target selection — verify before investing
- Cantina program data is server-rendered, not plain HTTP text. For one bounty, fetch the page HTML and decode the `self.__next_f.push([1, "..."])` chunks, including the `N:T<hex>,` stream chunk that holds long markdown instructions; for the list use `https://cantina.xyz/api/v0/opportunities?status=live&limit=100`. Read the bounty's Instructions text for reward tiers: the API's `totalRewardPot` and `assetGroups[].rewards` can be empty even when Critical and High minima and maxima are written in the instructions. WHY: treating a missing API field as no payout undervalues the target and misranks the shortlist.
- Screening many programs down to one (list triage, saturation grading, pin/deployed checks, post-audit fresh-surface rule): references/target-screening.md.
- Verify a target's audit depth from the repo BEFORE committing to a full audit: read the README audit section and list `audit/`/`audits/`/`certora/` dirs. Hash the audit PDFs before reading them: adjacent version reports are often byte-identical apart from a date and a pinned commit, so dedupe by hash and read one copy instead of each. Well-paying public programs are usually audited by multiple firms + formal verification; thorough static reading of such code yields verified negatives, not findings.
- A research subagent's "less-audited / quiet" ranking is a CLAIM to verify against the repo, not a fact — small codebase ≠ less-audited (a few-thousand-LOC repo can carry 8+ audit reports + Certora). Confirm before pivoting effort to it.
- Verify ELIGIBILITY GATES (reputation / submission fee / KYC / PoC) from the LIVE program page, never from a curated target list or aggregator — those carry stale gates (a list entry marked "rep >50" can actually require 100–150, silently excluding the operator). HackenProof program pages are client-rendered now: a raw `urllib`/curl fetch returns the SPA shell (~130 KB) with NONE of the gate terms in it (no "KYC", no tier amounts), so read the page in a real browser and work from `document.body.innerText` — a plain-HTTP fallback that used to work is a false-negative generator. Find the slug by search, never by guessing the protocol name: an umbrella program is named for the ecosystem, not the project (Fulcrom lives inside `programs/cronos-zkevm-smart-contracts`; `programs/fulcrom` 404s), and one umbrella page covers many projects — confirm each of YOUR addresses appears in its scope table. That table is truncated: click "Show all targets" before extracting or you miss in-scope targets. The reward/rules sections sit behind tabs, so `innerText.find("<section heading>")` matches the TAB LABEL first — regex the tier/amount lines (`\$[\d,]+ ?- ?\$[\d,]+`) or take the LAST match rather than the first. GitBook docs serve clean markdown at `<page>.md`, which also returns FAQ accordion bodies that never appear in the page innerText until clicked — read the `.md` instead of scripting a click at the accordion.
- Recon the PAID-IMPACT CATEGORIES and the exclusion list, not just the severity/reward table: a program can advertise Critical/High tiers yet pay only for narrow demonstrated impacts (e.g. loss-of-funds or a whole-validator-set chain freeze) and $0 for everything else — single-node panics, DoS-by-load, economic/governance design, third-party deps. Per-repo tier labels mark where impact is likely, not entitlements. Weigh submissions-vs-total-rewards-paid (many submissions / $0 paid = high rejection rate or slow triage) and any report-within-N-hours-of-discovery rule before committing. Extract the program's FULL in-scope target list and confirm YOUR target (chain + contract address) is on it — Nuxt/Next SSR pages bury it in an escaped JSON array whose object fields are indices into a deduped string table, so parse with backslash-free regexes and resolve the indices; a target that is absent, or only listed on another chain, wastes the whole submission. Treat a $0 reward tier as a gate, not a footnote: fee-logic/DoS/"lost revenue" findings pay nothing there — either build the funds-loss path or do not file. Read the payout FORMULA too, not just the tiers: a program that caps Critical at a percentage of economic damage (Cronos zkEVM: 10 %) turns the report into a quantification exercise — put a computed funds-at-risk figure and its honest bound in the draft, because the cap is arithmetic on whatever damage you demonstrate rather than a flat tier. Note the program's PoC constraints and state compliance with them (e.g. a cap on the monetary value a PoC may involve, such as $300 — a small local harness clears it, a mainnet-scale demo would not). KYC is normally collected only after a report is deemed valid, so do not have the operator do it up front. When the program carries a discovery→report clock ("reported no later than 24 hours after discovery"), filing already-proven findings outranks extending the hunt.
- **Docs-native programs (no platform): read the docs Security page's award TABLE, every cap, and the known-bug list before investing.** Project-run programs put scope, a payout table, a UTC deadline and often a monthly award CAP (a ~$1.5k/calendar-month ceiling queues confirmed awards into following months) in their own docs/`SECURITY.md`, and take reports via the repo's GitHub private-advisory form or a `security@` address — reporting format differs from platform gates, and a failing Foundry test is typically named as the most useful PoC. "Already known" can be a verifiable PUBLISHED list (some protocols time-stamp known bugs on-chain); read it plus the accept/reject reasons of any recently closed round or tooling bug hunt — those reasons are the precedent list for what the graders reject (mocks/stubs, wording-only, unreproducible reports), and tool-bug rounds pay on a different scale ($100-grade) than the funds-at-risk tiers. Compare the deadline against the current UTC clock before proposing the hunt.
- Cross-check every scope entry against the org (`gh api orgs/<org>/repos?per_page=100&sort=pushed`) — listed repos can be missing or private — and record each in-scope repo's HEAD SHA (`gh api repos/<org>/<repo>/commits/main --jq .sha`). If scope repos are being pushed DURING recon, the main branch is moving: "already fixed on main" / pinned-commit clauses then invalidate stale PoCs, so re-verify the pin right before submitting.
- A hacked protocol's PUBLIC upstream repo is often the PRE-hack vulnerable version — its headline bug is already disclosed (OUT OF SCOPE), and the real bounty scope is a KYC-gated post-fix mirror (e.g. `hackenproof-public/*`, access needs KYC + a paid-report threshold). Check the repo `pushed_at` against the hack/fix date and confirm the scope commit matches the deployed/post-fix version before auditing; don't burn effort re-finding the disclosed hack in stale public code. Surface the access gate to the operator early — it determines which version is actually auditable.
- Prefer novel/under-tested surfaces (new oracle types, PT/YT or flash-loan mechanics, async RWA integrations, cross-contract orchestration) over mature cores; fresh code + low submission rate beat raw ceiling. Do not endlessly pivot among equally-audited targets — the edge is novel surfaces + dynamic testing, not more reading of proven-sound code. 'Less-audited' and 'high-reward smart-contract program' rarely coexist: high-cap SC programs (L1s, major DEX/lending/oracle) are routinely multi-firm audited (MoveBit/OtterSec/Veridise/CertiK/BlockSec) + formal verification, so the genuinely less-audited surface on a bounty platform is usually web2/app (trading terminals, CEX frontends) — a different toolchain (dogfood/API recon). Confirm the operator wants that skill-shift before pivoting, instead of looping through equally-audited SC targets hunting a 'less-audited' one that does not exist.
- Clone targets with WSL git into `/mnt/e/audit/<name>` (Windows-readable for native Foundry, reliable network): shallow clone, then `git fetch --depth 1 origin <pinned-commit> && git checkout FETCH_HEAD` to land on the bounty's pinned scope.
- **When a small repo's shallow clone stalls or fails, fetch its tarball instead of retrying git:** `GET https://codeload.github.com/<org>/<repo>/tar.gz/refs/heads/<branch>` with urllib, then `tarfile.open(fileobj=io.BytesIO(body)).extractall(<audit-dir>)`. Try `main` before `master`. This yields the same tree (including vendored `lib/` and `dependencies/`) in seconds and avoids a network hang that otherwise consumes the whole session. Verify the extracted README's stated commit/provenance before auditing the files.
- For source-only programs with no published address list, run `chain-scope-guard` before any RPC or fork work: empty In Scope, the chain wildcard in Out of Scope, repository URLs and pinned SHAs in Special Rules. Keep every PoC on a local fork and record the guard verdict in the evidence bundle.

## Pulling verified source (no API key)

1. **Blockscout v2 API is free, no key**: `GET https://{chain}.blockscout.com/api/v2/smart-contracts/{address}`. Ethereum = `eth.blockscout.com`. NOTE: plain curl to `base.blockscout.com` gets Cloudflare — fetch its API same-origin from a browser tab instead (see references).
2. **The proxy verification bundle contains the FULL monorepo.** A verified ERC1967Proxy returns `source_code` (the proxy) PLUS `additional_sources` (list of `{file_path, source_code}`) = the entire import graph, often including sibling contracts deployed on OTHER chains from the same repo. Extract `source_code` + all `additional_sources` to a tree keyed by `file_path` — you frequently get the whole protocol without touching each chain's explorer.
3. **Implementation address key is `address_hash`** (not `address`) inside `implementations[]`. To follow proxies independently, read the EIP-1967 slot via RPC: `cast storage {proxy} 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc --rpc-url {rpc}`.
4. **Public RPCs that worked**: Base `https://mainnet.base.org`; Ethereum `https://eth-mainnet.public.blastapi.io`, `https://ethereum-rpc.publicnode.com`, `https://eth.drpc.org`, `https://1rpc.io/eth`. (`eth.llamarpc.com` was down.) BlastAPI served current-block `createSelectFork` state without a key. For fork tests pinned to an OLD block, use an archive-capable endpoint: publicnode returns HTTP 403 asking for a token, drpc serves archive state but rate-limits when many forks are created in parallel, and `https://rpc.flashbots.net` serves recent archive state well enough for `cast run <tx> --rpc-url https://rpc.flashbots.net --quick` but prunes older history. Do not write off flashbots entirely because an old-block read failed: a recent mainnet transaction can still be traced there, though each replay is slow enough that a mass trace over public RPC is not practical. `debug_traceTransaction` is absent on most free RPCs, and Blockscout v2 `/api/v2/transactions/<tx>/internal-transactions` lists internal calls without their `input`, so neither is a drop-in source of internal calldata when a tracer is unavailable. Run one `--match-contract` suite at a time on drpc; a full suite that recreates a fork per test hits the public rate limit even when the endpoint itself is healthy.
5. Fallbacks if Blockscout fails: **Sourcify v2 API — the FIRST check for chains with no Blockscout (Monad=143, HyperEVM=999, etc.)**: `GET https://sourcify.dev/server/v2/contract/{chainId}/{address}?fields=all` returns `sources` (full file map), `abi`, `storageLayout`, `runtimeBytecode` + `runtimeMatch`. Worked case: Veda's newest unreleased-in-repo teller generation fully recovered this way (33 files incl. two contracts absent from the public repo) even though every Monad explorer (monadvision/monadscan) is Cloudflare-walled — always try Sourcify BEFORE committing to decompile-only effort, then verify `runtimeMatch: match` and match `runtimeBytecode` length against `eth_getCode`. Older `/server/files/{chainId}/{addr}` endpoint often lacks records; the v2 one had it. Also: explorer HTML scraping; Etherscan V2 API needs a key. Docs sites: GitBook serves clean markdown at `<page>.md`, index at `/llms.txt` lists sub-pages (e.g. contract-addresses/{smart-contracts,creditors,asset-managers}.md) — grep for `0x[a-fA-F0-9]{40}`.
6. **Cronos / Cronos zkEVM (no Blockscout, no API key)**: the explorer is Next.js. Fetch `https://explorer.zkevm.cronos.org/address/{proxy}` and parse `__NEXT_DATA__` → `props.pageProps.data.contract` + `implementationContract`; file keys are in `s3FileKeys`, each file served at `GET /contract/cronos-mainnet-zkevm//{key}` (double slash, no address re-encoding). Pace ≥3.5 s per request with retry+backoff — the host 429s aggressively (34/34 contracts pulled only after pacing). Cronos mainnet = `explorer.cronos.com`, same pattern. zkSync-style chains cannot be forked by standard Foundry, so build a local harness from the pulled source instead of fork tests. **Verification detector + proxy pitfall:** `__NEXT_DATA__` carries `s3FileKeys` only when THAT address is verified, and a proxy is verified separately from its implementation — read the impl from the EIP-1967 slot and check both (a verified proxy sitting on an unverified impl is the common shape, so "the explorer says verified" is not a licence to skip the impl check). Sourcify has no records for chain 388 (`repo.sourcify.dev/contracts/{full_match,partial_match}/388/{addr}` → 404). zkEVM executes ZK-Stack/EraVM bytecode: never compare deployed bytecode across chains (zksolc output is several times solc's size) — identical SOURCE with different code hashes is expected, so cross-chain equivalence claims stay at source level.

BaseScan source extraction (no key, verified working): GET `https://basescan.org/address/{addr}#code` with a browser UA returns ~1MB HTML; the FULL verified import graph is embedded in checkbox attributes `data-cname='<file path>' data-csource='<source>'`. Regex-extract the pairs, `html.unescape` both, write a tree keyed by cname — you get the whole monorepo bundle to byte-diff against repo commits (pin the deployed version; repo HEAD may be ahead/undeployed = out of scope). Confirm liveness with `eth_getCode` batch RPC (publicnode endpoints tolerate batches; official Base RPC rate-limits 25 req/s, OP/Unichain reject large batches with 413 — chunk ≤8).

## Foundry project setup for a pulled tree

- `foundry.toml`: `src = "src/tree"`. DO NOT pin `solc_version` — pulled trees mix pragmas (`=0.8.30`, `=0.8.22`, `^0.8.24`); let Foundry auto-download multiple solc versions.
- Vyper-source repos need `vyper` on PATH before `forge build`, or Foundry stops with `Error: Found Vyper sources, but no compiler versions are available for it`. Install once with `uv tool install vyper`, export `PATH="$HOME/.local/bin:$HOME/.foundry/bin:$PATH"`, and confirm with `vyper --version`.
- For a pulled Foundry repo whose Solidity imports resolve through `node_modules`, run `npm install --ignore-scripts --no-audit --no-fund` before building. This satisfies the import graph without executing lifecycle scripts from an untrusted bounty repo; then run `forge build` as normal.
- On Windows/git-bash, `forge install` can fail with `Access is denied` (submodule/symlink path). Clone forge-std directly instead: `mkdir -p lib && git clone --depth 1 --branch <tag> https://github.com/foundry-rs/forge-std.git lib/forge-std`. Verify with `forge remappings` before blaming contract code. Why: the failure is the installer's filesystem path, not the dependency or the repo.
- Foundry refuses sources outside the project root and its own `lib/`, so install npm Solidity deps into a scratch dir then mirror them INTO the clone (`lib/node_modules`), not a sibling workspace. git-bash `cp -r` of a large `node_modules` can stall mid-copy; use `cmd.exe /c robocopy "<src>\node_modules" "<dst>\lib\node_modules" /MIR /NFL /NDL /NJH /NJS /NP /R:1 /W:1` and check the entry count afterwards. Point `remappings.txt` at `lib/node_modules/...`.
- Do not pin `solc` / `solc_version` when the clone mixes pragmas: pinning makes Foundry report "No compiler version exists" for older vendor files (`=0.6.12`) even though auto-detect handles several solc versions. Add `skip = ["contracts/**/vendor/*.vy"]` for Vyper vendor files instead of compiling them.
- A package whose auto-remap already includes a trailing `/contracts/` (e.g. `solidity-bytes-utils/=lib/node_modules/solidity-bytes-utils/contracts/`) breaks imports written as `solidity-bytes-utils/contracts/BytesLib.sol`. Add an explicit remapping WITHOUT the suffix to override the auto-detected one, and confirm with `forge remappings | grep <pkg>`.
- With `forge-std/=lib/forge-std/`, imports inside new tests must be `forge-std/src/Test.sol` (the auto-remap `forge-std/=lib/forge-std/src/` would make `forge-std/src/...` resolve to `src/src/...`). Pick one remap convention and write every import to match it before running a focused suite.
- **A checked-out target repo with recursive submodules can fail to compile from duplicate nested `forge-std` copies plus broken auto-remappings, not from contract code.** Copy to a scratch worktree, delete only nested copies (`find lib -mindepth 2 -type d -name forge-std`), keep the top-level `lib/forge-std`, and write an explicit `remappings.txt` with every import root the sources use (`forge-std/=lib/forge-std/src/`, `<lib>/=lib/<lib>/`, `@openzeppelin/contracts/=lib/openzeppelin-contracts/contracts/`, etc.). Why: Foundry's auto-detected remappings omit plain lib-name roots and concatenate nested remapping files into malformed entries, so imports still fail after the duplicate `deployCode` definitions are gone. Do not park a target on a compile collision before trying this.
- Add explicit remappings or `@` imports fail to resolve: `@openzeppelin/contracts/=src/tree/@openzeppelin/contracts/`, `@openzeppelin/contracts-upgradeable/=...`, `@layerzerolabs/=src/tree/@layerzerolabs/`, `contracts/=src/tree/contracts/`, plus any other top-level import root (e.g. `core-contexts-contracts/`).
- `forge build` then runs forge-lint automatically; most warnings (reentrancy-events, unsafe-typecast, locked-ether) land in standard OZ/LZ libs — filter to the protocol's own `contracts/` before treating them as findings.
- Scope the build to dodge nested-submodule/remapping rabbit holes: `forge build src/<cluster>/<Contract>.sol` compiles just that import graph. Full-project `forge build` can fail on unrelated libs (e.g. v4-periphery `@uniswap/v4-core` remapping) even when the target cluster is fine. `slither src/<cluster>` uses crytic-compile's foundry SCOPED build internally (`forge build --build-info --deny never src/<cluster>`) — works even when full `forge build` fails, and needs no svm solc (Foundry 1.9 embedded compiler). In a worktree run `git submodule update --init --recursive --depth 1` and verify `git submodule status --recursive | grep -c '^-'` == 0 before building. A submodule can show checked-out in `git submodule status` (gitlink commit matches) while its working tree is EMPTY, and plain `git submodule update --init` then no-ops (exit 0) — if a lib import fails 'File not found' despite status looking clean, repopulate with `git submodule update --init --force --depth 1 <path>`.
- Slither High `reentrancy-balance` on a balance-check-after-external-call is often the DESIGNED guard (e.g. detecting skipped signature verification), not a bug — confirm the reentrancy guards (onlyCaller/transient-lock/nonReentrant) before treating it as a finding.
- **Foundry refuses any source outside the project root + its own `lib/`** (`Error (6275): File outside of allowed directories`), so a second project (a fork-PoC dir next to a fuzz harness) cannot remap `../other-project/lib/...`. Copy the libs into the new project (`cp -r ../other/lib/forge-std lib/` — cheapest and reliable; git-bash `cmd //c mklink /J` junctions are flaky), and keep `fs_permissions = [{ access = "read", path = "./" }]` in its foundry.toml when a test loads a JSON fixture via `vm.readFile`.

## Static audit checklist (omnichain / ERC4626 / LayerZero)

Verify each trust boundary; these are where criticals live:
- **Cross-chain ingress**: `OAppReceiverUpgradeable.lzReceive` must enforce `endpoint == msg.sender` AND `_getPeerOrRevert(srcEid) == origin.sender`. All `_lzReceive` overrides sit behind it. `setPeer`/`setDelegate` must be `onlyOwner`; `_getPeerOrRevert` reverts on unset peer.
- **Mint/burn authority**: who can mint/burn the underlying/share token? Gate must be a single trusted role/contract (e.g. onlyAccountingReceiver), not open.
- **Replay protection**: cross-chain handlers should track processed GUIDs.
- **ERC4626 global vs local**: if `totalSupply()` is overridden to a cross-chain global value while `totalAssets()` stays a local balance, trace whether assets consolidate to the accounting chain — usually BY DESIGN, not a bug. Confirm conservation before claiming.
- **Compose atomicity**: `lzCompose` try/catch refund; `handleCompose` onlySelf; sub-call revert rolls back state (no double-spend). Check refund uses of `tx.origin` and refund-send failure (funds stuck).
- **Withdrawal queues**: fulfilled/canceled guards => exactly-once; checks-effects-interactions before external calls; nonReentrant presence/absence asymmetries.
- **Deployment**: factory `DEPLOYER_ROLE`, CREATE2 + init in same tx (no proxy takeover); registry setters role-gated.
- **Rounding/dust**: `_toSD`/`_toLD`/`_removeDust`, sharedDecimals conversion, ERC4626 virtual offset (`_decimalsOffset`). Fee-on-transfer assumptions.

## Wrapper-token / custodied-claim systems (burn-on-transfer + core-contract seams)

When a token wrapper burns balances sent to non-allowed addresses (merkl-style wrappers: `_afterTokenTransfer` burns when `isAllowed[to] == 0`), audit every CORE contract that can legitimately receive that token — not just claims:
- Enumerate the core's accepted-token list on-chain (public array getters like `rewardTokens(uint256)` via batched `eth_call`) and classify each entry: wrapper vs plain token, proxy vs immutable (EIP-1967 slot `0x360894a…`: nonzero = upgradeable/deprecated gen, zero = immutable gen). Addresses that revert on a later-added getter (e.g. `isAllowed`) are an older generation — split generations before claiming coverage; only the current immutable gen counts as in-scope fleet.
- The killer pattern: accounting credits a deposit that the token then destroys in the same tx (deposit flow `transferFrom(sender → core)` + burn-on-receive in `_afterTokenTransfer`) → funds burnt, phantom balance, and every later spend/withdraw reverts. Check `increaseTokenBalance`-style predeposit paths, fee paths, and any recovery function (`recover` can never return what was burnt).
- Byte-match a live immutable instance by re-deploying from repo source with the SAME constructor args on a fork and comparing `keccak256(addr.code)` — immutables are baked in, so this is exact and doubles as deployed==source proof.
- Honest bounds for such findings: check `creatorBalance(user, wrapper)` over live holders/funders and grep shipped UI bundles for the deposit function before claiming historical loss; state "mechanism live, no historical loss observed" plainly.
- **Enumerate the whole multi-chain fleet from the repo's own deployment records**: `deployments/<batch>/json-files/0 - Done Networks/*.json` are Gnosis-Safe `upgradeTo` batches; `transactions[0].to`/`[1].to` give the DC/Distributor PROXY addresses per chain — and they are the SAME address on every chain (Merkl: DC `0x8BB4C975…`, Distributor `0x3Ef3D8bA…`), so enumerate `rewardTokens(uint256)` per chain over public RPCs (~45/52 chains reachable via publicnode/drpc/onfinality + browser UA; 170-byte code = ERC1967 proxy = old gen). Detail fetches: batches of ~4 addresses × ~16 calls; bigger batches get silently truncated by public RPCs *while still returning a JSON list* — parse per-id and retry missing ids individually. Getter probes MUST carry valid args — an empty-args `amountToTransfer(address)` call reverts on EVERY instance and reads as a false "absent" (made this mistake twice).
- **Identify which BUILD each live instance runs** by clustering runtime code length against locally-compiled artifacts (exact-byte match; `forge inspect` length = printed/2 − 1) plus selector probes, then `git diff <old-rev> HEAD -- <file>` for semantics. Merkl fleet re-verified this way: 54× new-build Allow (5686 B) + 18× pre-refactor Allow (5458 B, no `amountToTransfer`; the delta is the refactor ONLY — the old build's claim-to-holder was a wash transfer, no extra bug), Vault 7× new (6576) + 1× old (6364) on Arbitrum, Withdraw ×4 (6000), AaveDebt ×1 (6931, Ink); **no TGE/ClaimFee/Native anywhere in any rewardTokens fleet** — check live-variant presence before grading a candidate that targets those variants.
- **Check the repo's OWN tests before reporting any wrapper behavior as a bug**: Merkl's `test_Success_NoDebtPullsNothingAndBurnsWrapper` / `ClaimHigherThanDebtOnlyPullsTheDebt` show the AaveDebt debt-clip-consume pattern is by design, and its `test_Success_ClaimHigherThanDebtOnlyPullsTheDebt` etc. kill a whole candidate class. ERC4626 zero-shares rounding in the vault variant is dust-only (zero-share threshold = share price in asset-wei; manipulation cost scales linearly with total shares = economically impossible) — do not report it.
- **Partner-built wrappers exist outside the repo — identify unknown live contracts before deep RE.** Mainnet `0x4399aad9` "XEF Merkl" (mXEF) turned out to be Xeffy's custom vested wrapper (allocate/batchAllocate/release/releaseFor/released/locked/vestedAmount/tgeTimestamp/CLIFF_DURATION), absent from every branch/history of merkl-contracts and unverified on Blockscout/Etherscan/Sourcify. Then SCOPE-CHECK: a partner contract is not a protocol bug, and decompiling 7 kB for a ~$1-2k partner book is a losing trade — document and close.
- Re-running Slither on the wrapper cluster adds nothing to this family — expect and verify these FPs once, then skip them: `arbitrary-send-erc20` on every holder-pull hook (holder is constructor-FIXED and consents by approving; only the recipient is caller-chosen), `reentrancy-eth` on the ETH-sending claim hook, OZ-library `incorrect-exp`/`divide-before-multiply` noise, and `uninitialized-local` on `DistributionCreator._pullTokens._feeRecipient` (assigned+used only under `fees > 0` — benign). Merkl run: 50 contracts / 211 results, zero real findings.
- **Multichain coverage starts from the repo's own deployment records, not the docs site.** A `deployments/` batch of Gnosis-Safe JSONs (`<id> - <Chain> Upgrade <stamp>.json`) carries the live PROXIES in `transactions[].to` (DC + Distributor), and deterministic deploys put the SAME proxy address on every chain — one `eth_getCode` probe per chain then finds the whole fleet. Docs sites get rewritten and their `.md` paths break; the repo is the stable map. A dead RPC under thread-pool load is NOT a dead chain: re-probe sequentially with alternate endpoints before declaring it unreachable (5+ chains came back this way). Runnable two-stage recipe + RPC candidate table: `scripts/multichain_fleet_scan.py`.

A missing id decoded as `None` is indistinguishable from a revert and silently fakes whole-chain results (this faked a full first pass). Write per-chain output files; re-run files marked `skipped` — the scan resumes.
- **Classify wrapper variants without ABIs**: getter presence first (`claimFeeRate()` / `unlockTimestamp()` / `debtToken()` / `vault()` / `pool()` — value vs revert), else runtime-code length against the locally compiled artifact's `deployedBytecode` length (±2 bytes metadata tolerance; <400 bytes = proxied old-gen instance). `amountToTransfer(address)` responding marks the current immutable gen — and it needs an address ARGUMENT: a selector-only call reverts even when the getter exists. DC proxy code length is itself a proxy-generation fingerprint (~171/178/210/232 B and ~834 B shapes seen across chains).
- **Wrapper post-condition fuzz (validated end-to-end)**: real ACM/Distributor/Creator proxies + one concrete wrapper; handler actions mint / fundDistributor / claim / claimToFeeRecipient / transferBetween / toggleAllow / setCap / setHolder; accumulate ghost counters per op — pulled underlying exactly equals the independently re-derived `_underlyingToTransfer(to, amount)` spec, a non-allowed recipient's balance never INCREASES, `supply == sum(tracked balances)`, holder underlying never increases — then assert the counters in `invariant_*` functions (an `assertEq` inside the handler body can be swallowed by the runner and pass vacuously). Verified by-design edges, do not re-report: `burn(distributor, x)` reverts (the burn hook re-enters the pull branch and pays `address(0)`), and `setAmountToTransfer` caps are IGNORED by the PublicWrapperBase children (`_onClaim` never consults `_underlyingToTransfer` — feature no-op, informational at most).

## GMX-v1-fork perp DEXes (broker fee / deposit fee / liquidation accounting)
Fulcrom = GMX v1 fork. Method that produced confirmed results: pull BOTH chains' verified source, then diff `Vault/VaultUtils/PositionRouter/Router` against `gmx-io/gmx-contracts` FUNCTION-BY-FUNCTION (strip comments, normalize whitespace) — the fork's own edits are where bugs live (`transferOutTokens`, `_collectFees` arg, broker-fee plumbing all surfaced this way). The SOURCE of a fork's core contracts is often identical across that protocol's chain deployments (Fulcrom chain 25 ≡ zkEVM) → verify the diff once, it applies to both; the deployed CODE still differs when one chain is built with a different toolchain (zkEVM = zksolc), so phrase the cross-chain claim as source-level.
- **Resting config is not a pause — check the leverage bracket before declaring a finding unreachable.** GMX v1 forks keep `Vault.isLeverageEnabled == false` and `marginFeeBasisPoints == maxMarginFeeBasisPoints` at rest, and the router brackets every position call: `Timelock.enableLeverage(vault)` (flag true, cheap fee e.g. 5 bps) → vault/OrderBook call → `Timelock.disableLeverage(vault)` (flag false, punitive fee e.g. 500 bps). Establish reachability from `Timelock.isHandler(positionRouter)` / `isHandler(positionManager)` + `Vault.gov == timelock` + the two Timelock fee values — never from the resting vault flags alone. Corollary: an entry point that is NOT a Timelock handler cannot flip the flag, so the OrderBook executes orders correctly only when reached through `PositionManager.executeIncreaseOrder` (handler + `onlyOrderKeeper` + brackets); calling `OrderBook.executeIncreaseOrder` directly hits `_validate(isLeverageEnabled, 28)` and reverts. Name the entry point that works instead of writing "increase orders can never execute" (a delivered report carried exactly that wrong conclusion).
- Bug class the diff catches: a handler passing `msg.sender` where upstream passed the request struct field. `PositionRouter.executeIncreasePosition → _collectFees(msg.sender, …)` makes `_shouldDeductFee` read the EXECUTOR's book; on the keeper/batch path (`executeIncreasePositions` → `this.executeIncreasePosition`) `msg.sender` is the router itself with no position → the 0.3 % deposit fee is silently skipped on every such request (proved with a self-vs-keeper-vs-batch differential PoC on `feeReserves`). Grep every fork hunk for `msg.sender` vs the request account.
- Broker-fee plumbing: `brokerFeeBasisPoints` comes raw from the user's `IncreasePositionParams` (no cap anywhere — `getBrokerFee` is just `size*bps/10000`), and `liquidatePosition` does `feeReserves -= brokerFeeAmount` after `validateLiquidation` may have capped the credit to remaining collateral (Case B) → underflow Panic(0x11) ⇒ a position with a broker fee can become IMPOSSIBLE to liquidate. Check `usdToTokenMin` vs `usdToTokenMax` rounding on both sides before claiming the revert.
- **Write the liquidation revert as an exact inequality, then count the liquidation routes.** Broker-fee revert condition: `feeReserves_before + min(marginFees, remainingCollateral) < usdToTokenMin(brokerFee)` — with `feeReserves = 0` (the state of a fresh/quiet deployment) it reduces to `remainingCollateral < brokerFee`, i.e. essentially the whole pre-default band for a large user-chosen `bps`. Then read `inPrivateLiquidationMode` and `isLiquidator(...)`: when public liquidation is off and the PositionManager is the sole liquidator, the reverting call IS the protocol's only risk-reduction path — no third-party keeper can work around it and `partialLiquidate` only runs for state `2` — which is what upgrades the accounting flaw from "keeper nuisance" to LP bad debt. Check the liquidation path's fee bracket too (the position fee used at liquidation comes from the vault's `marginFeeBasisPoints` *inside* the bracket, so parameterise the harness to the bracketed value, not the resting one).
- **Feature-specific event ≠ feature in use — decode the parameter words and count the non-zero ones.** A fork emits the feature event on every operation with zeroed fields when the feature is off (e.g. `IncreasePositionByBroker` fires for each increase with `brokerAddress = 0x0, brokerFeeBasisPoints = 0`), so counting the event overstates usage. Scan a window, decode the address/bps words yourself, count the real users, and put that number in the draft's bounds ("feature exposed and one parameter away, no position uses it in the last N blocks") instead of implying funds are at risk today.
- Do NOT claim "attacker drains funds" in this family before checking the open-time gate: `validateLiquidation(_raise=true)` during increase requires `collateral − openFee ≥ positionFee(size) + brokerFee(size)`, so the trader locks ≥ 2×(positionFee+brokerFee) and each bps×size payout is paid from that locked collateral → trader net ≤ −2×positionFee. The provable impacts are the liquidation DoS and unbacked `feeReserves` (claims > token balance), not theft.
- Measure the deficit instead of asserting it: accrue funding (warp), then `deficit = poolAmounts + feeReserves − token.balanceOf(vault)` and assert `deficit ≤ accruedFundingFee` + `attackerNet ≤ 0`. Test any hypothesis that the fork's new parameter (broker fee) is the root cause by running the SAME geometry with `bps = 0` — the Case-A uncapped `marginFees` credit reproduces the deficit without it.
- **A revert-based DoS has a damage WINDOW — find its exit before quantifying.** The un-liquidatable band is `remainingCollateral < brokerFee` while `feeReserves` is small; it ends when the losses pass the collateral, where the uncapped Case-A credit lets the broker debit succeed and the very same liquidation goes through. Bound the extra exposure by the window (≈ the position's remaining equity — single-digit USD on a $1,000 size / $200 collateral harness), never by the position size, and make the PoC SHOW the exit (a later-day liquidation that finally succeeds, plus a `bps = 0` control that liquidates immediately): a measured bound survives triage, a size-based claim gets downgraded by the reviewer's own arithmetic. Do not argue the window closes via fee income either — an ordinary position contributes ~0.5 % of its size, so covering a 90 USD broker fee takes ~180 same-size opens.
- Harness pitfall that silently zeroes time-dependent accounting: `lastFundingTimes[token] == 0` is a sentinel branch, and at `block.timestamp == 1` the seed write `block.timestamp/fundingInterval*fundingInterval` evaluates to 0 → funding never accrues. `vm.warp(block.timestamp + 2 days)` at the top of `setUp()` for any funding/EMA/epoch harness.
- **Collateral is credited from the Vault's BALANCE DELTA, not from an amount argument** (`_transferIn(token) = balanceOf(vault) − tokenBalances[token]`, then `tokenToUsdMin(that delta)` becomes the position's collateral; the cache is synced by `_transferIn`/`_transferOut`/`_updateTokenBalance`). This is upstream GMX v1 design, and it is safe only while every deposit reaches the Vault in the SAME frame as the vault call. Verify per path instead of assuming theft: the fork's `PositionRouter` escrows the deposit on itself at create (`pluginTransfer(path[0], user, address(this), amountIn)`) and transfers to the Vault immediately before `_increasePosition` at execution, so each delta is that request's own net deposit — the async OrderBook path was unverified and is the one place this check cannot be completed (flag it, do not claim it). The theft shape worth hunting is a stale deposit parked in the Vault across an execution boundary.
- **Enumerate every position path AND every custom guard's call sites; the fork's plugin path is the one with no bracket.** Fulcrom's synchronous `Router.pluginIncreasePositionV2` calls `Vault.increasePositionV2` directly, and its token pull `pluginTransfer(token, account, …)` gates on `_validatePlugin(account)` — so on that path the position owner is a whitelisted **plugin contract**, i.e. the integrating interface (which is also the party choosing `brokerAddress`/`brokerFeeBasisPoints`; the project's own FAQ calls that role the "On-Chain Wallet"). Use that as the concrete, documented route by which broker-style params enter production instead of writing "an integrator could". The same path carries no Timelock bracket and skips the fork's custom CircuitBreaker (wired into `PositionManager` and `PositionRouter` only): grep every custom guard's call sites and grade the gap by the gate that remains — the vault's `_validate(isLeverageEnabled, 28)` needs a Timelock handler (same rule as above), so a guard gap on a non-handler path is an observation, not a finding.
- **Auto-created orders (TP/SL attached to an increase): check WHICH size they carry.** Fulcrom's `PositionRouter.executeIncreasePosition` and `OrderBook.executeIncreaseOrder` both create the TP/SL decrease with `sizeDelta = request.sizeDelta` (the increment) and `collateralDelta = 0`, while the comment claims "fully close position". In GMX v1 semantics a decrease is a full close only when `sizeDelta == position.size`: `_reduceCollateral` returns the remaining collateral **only** in the `if (position.size == _sizeDelta)` branch, and `_decreasePosition` reverts (validate 32) when `sizeDelta > position.size`. Consequences to prove, not assert: (a) with a pre-existing position the TP/SL covers only the increment (residual exposure + all collateral locked in the remainder), (b) after any partial decrease the order is permanently unexecutable → a silently dead stop-loss whose pre-paid execution fee sits in the OrderBook. PoC shape that works: a `RecordingOrderBook` mock exposing `minExecutionFee()` (the router calls it — omitting it reverts `unrecognized function selector`) plus a self-executed increase request, then a `router.decreasePosition(collateralDelta=0, sizeDelta=partial)` differential vs a full close.
- PositionRouter execution paths differ in caller rules: the singular `executeIncreasePosition` is permissionless for the account after `minTimeDelayPublic` (differential PoC-friendly), while `executeIncreasePositions` (batch) is `_onlyPositionKeeper` and reverts `PositionRouterError(0)` = Forbidden — prank a registered keeper or use the singular form.
- **Unverified implementation on a chain that cannot be forked (zkSync/EraVM): fingerprint the function set.** Pull the same protocol's *sibling* deployment on another chain where the impl IS verified, extract each external function's selector (`cast sig` over signatures parsed from the source, skipping struct-arg functions), and grep the 4-byte hex in the target chain's `eth_getCode` — EraVM bytecode is a different format and 2-3x larger, but selector immediates are still present. Control: the same selectors must be found in the sibling's own runtime code (validates the method). 24/24 matches + identical live config getters is enough to audit from the sibling source while stating plainly it is not byte-identity.
- **Re-read every live number before writing the report's bounds section** — compressed earlier reads produced a wrong pool figure ("~$13k vUSD" vs the actual 223.6) and a wrong "proxy admin is an EOA" claim (it was a 6.6 KB admin contract). Fresh reads of `poolAmounts`/`reservedAmounts`/`feeReserves`/`guaranteedUsd` per whitelisted token, `gov()`/`admin()` per contract, and the price config (`spreadBasisPoints`, `isSpreadEnabled`, deviation bands, feed freshness `lastUpdatedAt` vs `priceDuration`/`maxPriceUpdateDelay`) cost minutes and are what a reviewer will check first.
- **Count how many times a fee is charged across ALL paths, then find which path does not fund it.** Fulcrom's broker fee is charged at open (from the deposited collateral) and again at close (`_collectMarginFees` → `_chargeBrokerFee`, still the position's own collateral), then a THIRD time inside `liquidatePosition` as a cash `_transferOut` out of the vault. The third charge has no funding source once the collateral is consumed — that asymmetry is the finding, and the two funded charges are what make the trader's own `decreasePosition` safe (verify the decrease path explicitly: if it is `_collectMarginFees`-funded and never debits `feeReserves`, the liquidation charge is the unbacked one by elimination). Same method for storage/reward accounting: enumerate the write sites, then ask which one lacks a matching inflow.
- **Surfaces in this family that closed as faithful/cosmetic ports — re-run the function diff, then skip them.** `Vester`, `RewardTracker`, `RewardDistributor`, `BonusDistributor` differ from `gmx-io/gmx-contracts` only in SafeMath sugar, `Upgradeable` suffixes and added initializers (the one real delta was a gov-only `hasMaxVestableAmount` flag wrapping the max-vestable check); the `PositionRouter` execution-fee payment/refund paths are consistent (fee paid once, on execute or on cancel, with the batch executor wrapped in try/catch); and the fork's `PositionManager` exposes ONLY a single-position `liquidatePosition` — no `liquidatePositions`/`...UsingGlobalSizes` — so do NOT claim that one reverting position blocks a batch, and do not expect batch amplification of the liquidation DoS.
- **Fee-conversion peripherals (FeeDistributor-style): check the swap for a slippage floor.** `swapExactTokensForTokens(subTotalFee, 0, path, …)` converts protocol fees with `minOut = 0` → the conversion is MEV-extractable from stakers' fees; on a ZK-Stack chain the sequencer's FCFS ordering cuts the classic mempool-sandwich exposure (a searcher must race a predictable keeper call instead of reading the mempool), so quantify against pool depth and expect Low rather than treating it as payout-grade.

## Static audit checklist (staking / derived asset-module integrations)

Thin wrappers over audited bases (Slipstream/Aerodrome/staking AMs) usually yield verified negatives; the integration overrides are where a real defect would live. Before calling one a bug:
- **Read the CALLEE implementation, not the interface signature.** A wrapper subtracting an account-wide accumulator from a per-position value looks like a scope mismatch, but the callee may already fold that accumulator into its return — e.g. a gauge `earned(account, tokenIds)` often returns `positionRewards + deferredEmissions[account]`, so `earned(...) - deferredEmissions(account)` correctly isolates the position share and cannot underflow. Confirm against the gauge/base source before claiming underflow/under-credit.
- **Trace whether a zeroed/empty override feeds PAYOUT or only VALUATION.** Claim flows typically pay the token balance-delta (`balanceOf(after) - balanceOf(before) - surplus`), not a view helper. A helper that only prices collateral (e.g. `_rewardAmount` feeding `underlyingAssetsAmounts`) and returns 0 is CONSERVATIVE under-valuation (users borrow less), not over-valuation/fund loss — an observation, not a finding.
- **Per-position staker clones vs pooled accumulator:** a `_getRewardBalances` override crediting the full claimed delta to one position (bypassing the base pro-rata rewardPerToken accumulator) is correct when each position stakes through its own deterministic clone; the pro-rata base is for pooled stakes. Check the staking topology before calling full-credit a mis-accounting.
- **Surplus invariant:** `claimableSurplus = bookedSurplus + balanceOf(this) - lastRewardBalance`; after a payout, `lastRewardBalance` must be set so `balanceOf - lastRewardBalance == 0` (no double-count). emergencyBurn forfeits unclaimed emissions but pays the booked position reward — verify it keeps this invariant.
- **NEAR LST (near-sdk, e.g. rNEAR-style):** cross-contract validator callbacks must be `#[private]` (predecessor==self) or they are spoofable — a missing `#[private]` on a balance/stake callback is a classic critical. Share math `shares = total_supply*amount/total_staked` rounds down, with init minting seed shares to self so total_supply>0 always (first-depositor inflation mitigation); `donate()` raising total_staked benefits existing holders (not a bug). A reward callback computing `rewards = new_balance - total_balance` (u128, overflow-checks on) underflow-reverts when a validator is slashed — confirm slashing is handled on a separate path (draining/failed-balance handler) before calling it a bug. NEAR PoC uses near-workspaces-rs sandbox, not Solana Anchor.
- **Multi-step swap slippage double-count (router / margin trading):** a slippage gate that SUMS `min_amount_out` over every step whose `token_out` equals the final token (or `amount_in` over steps whose `token_in` equals the first token) double-counts value when an intermediate token is reused as a later step's input (path A→B→A→B): the gate passes on inflated guaranteed output while the real final output is small, enabling forced-liquidation / reserve-drain via manipulated pools + fake tokens. The correct check uses ONLY the first step's `amount_in` and the last step's `min_amount_out`, never a sum over repeated tokens. Audit any multi-step swap/margin slippage summation for this; if this class was already exploited, the public pre-fix repo is out of scope — audit the post-fix version for incomplete fixes / variants.

## Solana static trust boundaries
- Account validation: every constraint (owner, signer, has_one, seeds/PDA, mint match, token authority). Missing checks = classic Solana critical.
- CPI return data: verify `get_return_data()` program_id == expected callee (anti-spoof); a callee revert aborts at the syscall.
- Arithmetic: check the crate `overflow-checks` profile — release `overflow-checks = true` means overflow PANICS/reverts, not wraps (changes exploitability of unchecked `+=`).

- Oracle: staleness (ts - price_ts vs max_age; future timestamps), exponent bounds, divergence/cap/floor composition, confidence-interval overflow.
- Trusted-role functions (delegate/admin via Signer + has_one) are NOT external bugs even when they look dangerous (e.g. unchecked add gated to that authority).

To prove a finding end-to-end without building the Anchor program: dump the deployed ELF (`solana program dump`), run it in solana-program-test via `prefer_bpf` + `tests/fixtures/<name>.so`, create state through the program's own instructions, control Clock via `set_sysvar`, and use a MAIN-vs-CONTROL differential. ## Dynamic invariant fuzzing — standalone harness (key technique)
Do NOT build the full Anchor/Foundry program to fuzz pure math. Copy the bug-prone PURE functions VERBATIM into a minimal crate pulling only their real deps, replicate the surrounding state machine faithfully, and fuzz invariants with a seeded RNG.
- **Prove reachability before building any harness for a newly discovered contract generation.** Pull the ABI (Sourcify/Blockscout), compute every selector with `cast sig`, query `isCapabilityPublic(targetAuthority, target, selector)` for ALL of them, then send a direct `eth_call` from a random EOA and from `owner()` to the candidate entrypoint. Zero public capabilities plus both reverts kills the surface before compute is spent. Why: sound internal accounting behind `requiresAuth` is dead code for an unprivileged hunter, and a fuzz campaign on an unreachable entrypoint proves nothing about payout.
- Solana deps: decimal-wad / fixed (Fraction = U68F60) + uint + rand. EVM: minimal Foundry project isolating the core contract cluster + concrete controller + LibClone proxies (for `_disableInitializers` constructors) + ghost-accounting invariant handler. Both recipes: references/solana-and-fuzz-harness.md.
- Invariants: conservation (sum user shares == global), solvency (sum claimable <= pool), no-profit-from-rounding (withdrawn <= deposited + donations), no-underflow in rounding-error paths (disinvest >= actual send).
- Run millions of seeded random op sequences; catch_unwind to count violations; print the offending sequence. 0 violations across millions of ops = strong soundness evidence.
- For periphery or router bugs, prefer a mock-only Foundry test over a fork: implement only the selectors the target actually calls on its collaborators (an `IStrategy`-typed argument only needs `DUTCH_DESK()`, `AUCTION()`, and `setProceedsReceiver()`), and drive the victim with a mock vault. This isolates control-flow defects such as stale-id checks and yields a passing PoC in seconds; add a fork reproducer only when the claim depends on real market state.
- When a Yearn-v3 tokenized strategy redirects withdrawal proceeds to a user through a transient receiver, `TokenizedStrategy._withdraw` re-reads the strategy's idle balance and books the redirected amount as a loss. Any caller-supplied `maxLoss < MAX_BPS` then reverts with `too much loss`, and the vault's redeem return value becomes 0 while the user receives proceeds externally. Treat a defect in the audited protocol's own router or strategy redirect as in-scope rather than a third-party Yearn issue, and measure cross-user balances before claiming funds loss.
- **A counter snapshotted once per supplied contract is a stale id for every callee after the first.** Routers that read a shared `nonce`/`epoch`/queue id up front and later validate each callee against that same snapshot will accept another callee's event (false pass, bypassing the caller's own minimum) or reject a healthy callee (false revert, bricking a multi-contract batch). Snapshot immediately before each callee action or have the callee return the id it produced. Prove it with a mock-only PoC first, then upgrade to two real contracts on a fork when severity depends on real orchestration.
- **Foundry invariant campaigns: size comes from the ENVIRONMENT, not a flag.** Foundry 1.9 rejects `forge test --invariant-runs` (`unexpected argument`); use `FOUNDRY_INVARIANT_RUNS=N FOUNDRY_INVARIANT_DEPTH=M forge test`. Measured locally on a Vault handler: 256×400 ≈ 128k calls in ~70 s single-core (256×500 ≈ 71 s), so the box is needed only for multi-million-call budgets — and a plain unit-test harness with `targetSelector(...)` is enough to start; no Echidna rewrite is required for the first campaign.
- **Budget the campaign with the invariant engine, not one giant test function.** A deterministic replay that loops `runs x depth` ops inside ONE `test_*` function hits Foundry's `gas_limit = 1073741824` (measured: 4x400 = 1,600 ops at ~930M gas passes; 16x400 and 256x400 OOG at `gas: 1073720760`, and a raised gas limit made a 102k-op transaction exceed 600 s wall-clock). Use `FOUNDRY_INVARIANT_RUNS=256 FOUNDRY_INVARIANT_DEPTH=400` for the 102k-call campaign (Foundry isolates each run, ~65 s) and keep a small deterministic replay (4x400) for exact ghost counters and decoded reverts. `FOUNDRY_GAS_LIMIT` did not override the test gas limit in 1.9.
- **Solidity 0.8.30 cannot `abi.decode(reason[4:], ...)` on `bytes memory`** (Compiler 1227/1956, index range only for calldata arrays). Copy the tail into a fresh `bytes memory` in a loop, then decode that. Read the revert selector with `assembly { sel := mload(add(reason, 0x20)) }` inside `catch (bytes memory reason)`.
- **Dutch-desk/auction seam detail:** when an auction's `current_amount == 0`, the desk computes `starting_price == 0` and `auction.re_kick` reverts `!starting_price` BEFORE its `!current_amount` check. An unclassified `Error(string)` residual in a revert ledger is often this gate, not a contract bug; label it before concluding.
- **Tune the handler or the campaign proves nothing.** Two failures seen live: (1) liquidating only when `validateLiquidation != 0` after random price moves never reaches the bands — 16 engagements in 128k calls and the deficit metric stuck at 0; fix with one op that moves the price ONE-DIRECTIONALLY relative to the position's own `averagePrice` (5–60% adverse) and liquidates in the same call, after a warp + funding update. (2) `withdrawFees` reverts at `_onlyFeeAdminOrGov` for the test contract, so the metric measures the gate, not solvency — grant the role (`vault.setFeeAdmin(address(handler))`) before trusting those counters. A metric that stays 0 across a whole campaign is a tuning bug until proven otherwise.
- **Report fuzz results PER CAMPAIGN, never aggregated across seeds, and keep a ledger file with one row per campaign carrying the code state that produced it** (which handler ops existed at that run). If a revert class or counter appears in some campaigns and not others, the honest claim is "reached but seed-dependent — the deterministic PoC is the evidence, the campaign is a soundness control"; a class reproduced once, or never, cannot be presented as reproducible. Separate the counters that measure the TARGET (state reached, reverts with their revert selectors decoded via `catch (bytes memory reason)` + assembly mload — Panic `0x4e487b71`/0x11 vs `Error(string)` vs empty) from those that measure the HARNESS (calls, discards, gate reverts) before concluding anything from a zero.
- **Shrink the position to satisfy absolute-value preconditions instead of widening the oracle move.** When a branch needs an absolute quantity under a cap (collateral value <= X) while debt must stay above a minimum: borrow the minimum, repay down toward the target debt, then withdraw at the full withdrawal limit repeatedly so collateral converges to debt/CF. This cut a required 98% price dip to 32%. Fork pitfall: `getWithdrawalLimit` often calls `getPrice`, which WRITES the day's low, so a low already present in fork state dampens every withdrawal and the position never shrinks — overwrite today's low with the high price first, then shrink.
- **Strip privileged setup from a PoC before finalizing.** Re-run the exploit with only the attacker's own signature/prank; an allowlist or role grant executed by the live governor is a privileged action and most programs exclude such attacks. If the permissionless path passes (e.g. `startPrank(attacker, attacker)` satisfies `msgSender == tx.origin && code.length == 0`), ship that version — otherwise the report is dead on arrival.
- **A harness that reaches a path only through `vm.mockCall` or `deal` is a local test artifact, not a payable PoC.** Label it as such, keep the finding count at zero, and name the real precondition still unproven. Why: funds-loss programs commonly require the condition to exist at the fork block and forbid storage edits or synthetic oracle prices; a passing mocked harness says only that the code path is reachable, not that an exploitable state exists today.

## Pre-submission verification pass (run before filing; parallelizable)

Four independent checks, each of which has caught a real defect that would have shipped:
1. **Re-run every PoC from scratch** on a clean build and diff its output against the quoted evidence. A PoC that cannot be re-run, or whose only evidence is a stored log, is a liability — fix the reproducer (unique bytes per transaction, pinned fixtures) before filing, not after a reviewer asks.
2. **Byte-compare every fixture against its live source** (program dump / account fetch + `cmp`/sha256). Byte-identity of the program ELF and the state accounts is the strongest no-cheating evidence available and costs one command per fixture.
3. **Re-verify every live configuration claim from fresh reads** — offsets, chains, limits, market membership via getProgramAccounts+memcmp — instead of trusting saved JSON, and record the values in one evidence JSON so every number the report cites has an artifact. When the claim came from an existing watch script, reuse that script's RPC endpoints, selectors and expected-state keys as the probe recipe instead of inventing endpoints; its state file is a prior observation, not current truth. Run the replay as a read-only probe that does not write the watcher's state file.
4. **Audit the documents against the artifacts**: inventory the report directory by mtime first, since an addendum newer than the main PDF means the main PDF is not the final report; recompute each quoted hash, confirm each number appears in a log, list internal contradictions (the same address/date/severity/claim stated differently across files), and flag anything the evidence does not support. When PDF text extraction looks scrambled, render the suspect page to an image and inspect text-block coordinates with PyMuPDF (`get_text('blocks')`) before calling it broken: negative x or clipped line starts prove a real off-page table, while a clean image with odd extraction order is an extractor artifact. Why: rebuilding a visually correct report wastes time, and shipping a clipped table hides the finding table from the operator. Fix artifacts AND documents, then re-issue the report under a new version suffix rather than silently overwriting it.
5. **Machine-verify every code citation.** A draft's `file:line` references drift as the tree or the draft is edited; script the check (`line N of file F must contain substring S`) and re-run it after the last edit. Verified-citation counts (e.g. 21/21) are cheap insurance against the one stale line a reviewer will find first.
6. **Keep a coverage-negatives artifact with the measured value that killed each lead.** When a targeted PoC falsifies a severity escalation, liveness claim, or reachability hypothesis, record the exact observed quantity (returned assets, balance delta, event count) next to the retracted claim, and re-run the artifact build after the edit. Why: a later session or reviewer will otherwise re-litigate a closed lead using the pre-measurement wording.

## Honesty rule

A static analyzer that cannot compile the target is a TOOL BLOCKER, never a CLEAN class: record the exact failure in the coverage ledger and either fix the toolchain or sweep that class by hand. Why: an analyzer that exits before emitting results leaves no artifact that could close the class, and writing CLEAN from a compile error overstates coverage to the next session.

A careful read of a mature, audited protocol often yields NO confirmed Critical/High — only low-severity observations. Report that plainly; do not manufacture a finding. Answer "how many findings?" with a count-by-category breakdown (submittable / informational observations / bugs in your own tooling / surfaces verified negative) rather than prose, and never restate a negative result as "the protocol has no bugs": name the coverage that was swept (surfaces + counts) and the residual surface you could not reach (e.g. rotated merkle roots leaving live leaf sets opaque), because the unfalsifiable version invites either false confidence or the next session redoing the whole sweep. The next value-add is dynamic invariant fuzzing (Foundry fork), not louder claims. Before claiming an edge-case bug, confirm it is REACHABLE under the protocol's input bounds — a defect behind a branch valid inputs never enter (e.g. an exponent-difference threshold producers never exceed) is dead code, not a finding. Always bytecode-match the pulled source against the target chain's deployed impl before submitting any finding (the bundle may be a different version).

## Differential fuzzing of bit-packed / stateful logic (proven on Solana, applies to EVM too)

When static reads keep closing as "sound", the remaining edge is state-dependent logic: circular buffers, bit trackers, EMA/TWAP accumulators, epoch math. Build a standalone harness that copies the target functions VERBATIM (adapt only framework types: errors, msg!, account structs) and diff against a naive reference model (e.g. Vec of timestamps vs a 64-bit window tracker). Check a security-direction invariant (tracker must never count samples older than the period), not just equality — conservative divergences are safe, overcounts are findings. Cross-check value arithmetic against an independent recompute to prove copy fidelity (0 mismatches = faithful).
- Bug class that static audits miss: **mod-N index aliasing** — a circular-buffer erase shortcut compares window indices mod N; a gap of ≈ one full period lands in the SAME index and skips erasure, leaving stale bits that inflate validity counters. Compare absolute epochs (ts*N/period without %N), not mod-N indices. Worked example: a production TWAP tracker's same-index erase shortcut → validity-gate bypass + EMA ≈ manipulated price after a near-period gap (α≈1).
- Run harnesses in WSL via script files with `. "$HOME/.cargo/env"` (wsl.exe bash without -lc lacks cargo PATH); CARGO_TARGET_DIR on native ext4 (/root/.cache) not /mnt/e for speed. Add a deterministic `repro` mode with a minimal hand-built sequence for the report.
- For CL/AMM pure-math fuzzing (swap/slippage/quadratic solvers), bound inputs to the REACHABLE domain or you drown in dead-code false positives: ranges tick-aligned (min width ~1 tick; real bounds come from `TickMath.getSqrtPriceAtTick(integer tick)`), balances above the fee threshold (dust positions revert on fees and are rounding-dominated), fees realistic (<=10%; ~100% fee is precision-degenerate), normalized params within the overflow guard (extreme price×balance/liquidity safe-revert FullMulDivFailed/Overflow). Check EVERY counterexample for reachability before treating it as a finding. Effective probe: standalone Foundry harness copying the math VERBATIM + a wrapper contract exposing internal fns + a liquidity-equality differential (L0==L1 at the analytic optimal price) + an amountOut-never-over-estimated bound. `via_ir=true` avoids stack-too-deep in instrumented repro tests. Heavy campaigns offload to Simular Box (transfer a tar.gz of the self-contained harness via base64 + box write_file; clone forge-std there).
- Fork-state lending-core invariant handlers (Arcadia proven): create a REAL margin account via Factory.createAccount(salt, version, creditor) rather than mocking, but match the account VERSION to the creditor's API — Arcadia AccountV4 lacks increaseOpenPosition (ActionManager architecture) so LendingPool.borrow NoFallbacks on V4; use V3. V3 deposit takes 3 arrays (V4 added a 4th assetTypes). Creditor is set by createAccount->initialize (calling openMarginAccount again -> CreditorAlreadySet). Internal state vars (LIQUIDATOR, minimumMargin, realisedDebt) have no public getters — read them via a public view that returns them (pool.openMarginAccount(version) -> liquidator_/minimumMargin_) or derive the invariant from public views (solvency: balance+totalAssets>=totalLiquidity; unrealised interest cancels). Borrow is bounded by pool IDLE balance, not totalLiquidity — over-borrow -> TRANSFER_FAILED. Drive liquidation by prank(account) startLiquidation + prank(liquidator) settleHappy/UnhappyFlow to test settlement accounting + bad-debt socialization (_processDefault) without the full Dutch-auction flow. Fund the invariant caller (vm.deal test contract + DEFAULT_SENDER 0x1804c8AB1F12E6bbf3894d4083f33e07309d1f38 + targetSender). Decode setup reverts by selector (cast sig over grep'd error defs): NoFallback=wrong selector/arity/version, TRANSFER_FAILED=insufficient idle liquidity.
- A proven logic bug in audited code is reportable even when economic impact is config-dependent: state preconditions honestly, propose severity with the config survey as the follow-up gate. Run that survey TRANSITIVELY — BFS the oracle/price reference graph, never one hop (wrapper chains like most-recent-of/multiplication chains produce false "no consumer" negatives) — and classify whether the guard each consumer relies on derives from the SAME manipulable source as its price: that class turns a tracker/stateful bug from conditional into a live path. Recipe + chain account layouts: solana-bounty-onchain-poc skill (§ Live config survey and its live-consumer-survey reference).
